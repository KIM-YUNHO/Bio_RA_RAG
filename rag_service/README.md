# RA RAG 서비스

코드 정리(2026-10-21): HTTP 계층은 FastAPI(`rag_service/app.py`)만 남았다. `--server` 인자와 표준 라이브러리 서버, 별도 검토 화면 `review_viewer`와 `--review-url` 인자, 이전 화면 `rag_service/static/`을 제거했다. 근거의 `review_links`는 `pdf_page`·`asset_id`만 담는다. 릴리스 묶음 읽기는 `rag/bundle.py`. 아래 날짜별 기록의 실행 명령에 나오는 `--review-url`·`--server`·`review_viewer`는 당시 기준이다.

FastAPI 전환(2026-10-18): HTTP 계층을 FastAPI로도 띄울 수 있다(`--server fastapi`; 시작 스크립트 `-Server`의 기본은 fastapi, `python -m rag_service`의 기본은 기존 표준 라이브러리 서버). URL·JSON·상태 코드·보안 헤더가 같아 화면은 바뀌지 않는다. 같은 검사를 두 서버에 돌리는 계약 테스트 `tests/test_http_contract.py`, 전체 테스트 1,326개와 RA DOM 검사가 두 서버에서 통과했고, 실제 데이터 16개 요청의 응답이 기존 서버와 같았다. `/api-docs`(명세 화면)·`/openapi.json`은 FastAPI 서버에만 있다. 8885가 FastAPI, 8775는 기존 서버로 운영한다. 계획: `docs/project/FASTAPI_MIGRATION_PLAN_2026-10-18.md`.

별도 원문 검토 페이지 연결 제거(2026-10-16): 상단 `원본 검토 페이지`, 답변의 `검토 페이지`, 근거 패널의 `검토 페이지에서 상세 보기`를 제거하고 시작 시 해당 링크를 설정하던 코드도 삭제했다. 원문 확인은 메인 RA의 근거 패널과 메모 상세 안에서 이어진다. 원본 PDF·기관 출처, 단계 메모와 검토 메모 기능은 유지한다. RA DOM 회귀 및 실제 데스크톱·모바일 원문 열람 검증을 통과했고, 8775·8885에서 제거된 진입점과 기존 원문 패널을 확인했다. 저장 데이터 변경이나 서버 재시작 없이 새로고침으로 적용된다.

적재 목록 펼침 상태 유지(2026-10-16): 대화 삭제 후 선택이 해제되면 `view.kind` 기준으로 대화 목록을 접던 동작을 수정했다. 대화·DB 릴리스 목록의 펼침 상태와 목록 스크롤을 다시 그리기 전 보존하여 삭제·검색·자동 갱신 때 복원한다. 직접 접은 목록도 자동으로 펼치지 않는다. 두 DOM 회귀와 8775·8885 실제 브라우저에서 시험 대화 삭제, 열린/접힌 상태의 실제 주기 갱신, 새로고침 후 삭제 유지까지 검증했다. 기존 사용자 대화는 변경하지 않았다. 정적 JavaScript 변경이므로 서버 재시작 없이 페이지 새로고침으로 적용된다.

적재 대화 삭제 운영 수정(2026-10-16): 직전 반영은 8775만 재시작하여 8885가 구형 API를 유지했다. 같은 최신 정적 화면을 읽어 삭제 버튼은 보였지만 8885의 삭제 POST는 404를 반환했고, 목록도 삭제 표시를 무시했다. 실제 실행 중인 8885를 동일 릴리스·모델·검토/대화 경로로 갱신했다. 두 포트 각각에서 새 빈 시험 대화만 만들고 실제 브라우저의 삭제 버튼 → API 200 → 목록 제거 → 조회 404 → 새로고침 후 미복원을 검증했다. 기존 사용자 대화 9개와 수집 요청은 유지했다. 오류는 창 하단 외에 삭제 확인 영역에도 바로 표시한다. 재현·검증은 `work/reproduce_ingestion_delete_live.py`와 `work/qa_ingestion_delete_fix_2026-10-16/`에 있다.

적재 대화 삭제(2026-10-16): 자료 수집·적재 창의 대화 목록과 대화 상단에 삭제 버튼을 추가했다. 확인 후 해당 대화를 목록·조회·이어쓰기에서 제외하고 작성 중 문구와 마지막 선택도 정리한다. 다른 요청을 보고 있을 때 대화를 삭제해도 요청 화면은 유지한다. `POST /api/ingestion/sessions/<id>/delete`는 같은 출처의 빈 JSON만 받으며, 응답 중인 적재 턴과 같은 DB 잠금을 사용하고 중복 삭제는 성공으로 처리한다. 수집·검토·등록 중인 요청의 소유 대화는 삭제를 막아 확인표 승인 경로를 유지한다. 완료·실패·취소 요청과 수집·등록 자료는 대화 삭제 후에도 보존한다. 마이그레이션 `009_ingestion_session_deletion.sql`의 `deleted_at`으로 표시하며 append-only 대화·작업 감사 기록은 지우지 않는다. 삭제 대화는 CLI로도 재개할 수 없다. 격리 PostgreSQL/HTTP 포함 17개 테스트, 에이전트 규칙 5개와 세 DOM 검증을 통과했다. 실제 Chrome 데스크톱·390px에서 버튼·확인·취소·진행 요청 보호를 확인했고 실제 대화 9개·30턴·수집 요청 1개와 기존 메모는 그대로 보존했다. 화면은 `work/qa_ingestion_delete_2026-10-16/`에 있다.

메모·근거 함께 보기(2026-10-16, 후속 사용자 피드백): 상세 메모에서 원문을 눌러도 메모 창과 읽던 위치를 유지한다. 데스크톱에서는 같은 창의 왼쪽에 메모, 오른쪽에 근거 원문을 나란히 표시하며 각각 스크롤한다. 먼저 열려 있던 근거도 상세 메모 안의 같은 위치로 옮겨 페이지·선택을 유지한다. 좁은 화면은 `메모 / 근거 원문` 전환 버튼으로 읽고 본문 스크롤을 보존한다. 근거 닫기 또는 첫 Escape는 근거만 닫으며, 상세 창을 닫으면 열려 있는 근거는 메인 우측으로 돌아간다. 원문 뷰어 DOM을 복제하지 않고 옮겨 중복 ID·페이지 재초기화를 피했다. 두 열람 순서·페이지 이동·닫기·모바일 전환을 실제 Chrome에서 검증했고, RA·자료 수집 DOM 회귀와 저장 데이터 동일성 검증을 통과했다. 모델 호출·실제 데이터 쓰기는 없으며 화면은 `work/qa_ra_memo_evidence_2026-10-16/`에 있다.

메모 질문 카드·채팅 정렬 개선(2026-10-16): 파이프라인의 RAG 메모는 원 질문을 먼저 표시하고, 클릭하면 최대 900px 상세 창에서 저장된 메모 전문·출처·태그를 읽는다. 직접 메모는 첫 줄을 표시한다. 새 RAG 메모는 저장 당시 사용자 질문을 출처에 보존하며, 기존 메모는 원 작업 기록에서 질문을 읽는다. 기존 본문·수정 이력은 변경하지 않는다. 처리 중 표시를 둥근 카드와 안쪽 여백으로 정리하고, 대화 이어가기 안내를 입력창 안에서 같은 시작선으로 맞췄다. 격리 PostgreSQL 포함 테스트 14개와 RA·자료 수집 DOM 검증을 통과했다. 실제 Chrome에서 데스크톱·390px 화면의 질문 카드, 저장된 긴 답변 전문, 입력창 정렬, 처리 중 표시를 검증했다. 실제 데이터 쓰기·모델 호출 없이 확인했으며 기존 메모 해시도 일치했다. 화면은 `work/qa_ra_memo_reader_2026-10-16/`에 있다.

본문 가독성·빈 메모 정렬·외형 재정리(2026-10-15): 원형 노드와 넓은 프레임을 번호형 단계 카드, 중립 회색 작업 배경, 정돈된 버튼·메모 카드로 변경했다. 메모가 없는 단계에는 정렬된 추가 카드를 표시하며 클릭하면 그 단계가 선택된 메모 편집 창이 열린다. 안내문은 어절 묶음으로 줄바꿈하여 ‘메모/를’ 같은 분리를 피한다. 답변·입력은 최대 900px, 선택 단계 메모는 최대 880px로 제한하고 16px 본문은 유지했다. 전체 보기의 단계·메모 열과 빈 카드 안내문 시작선을 실제 Chrome 렌더링으로 확인했다(차이 0px). 저장된 답변과 모바일도 실제로 렌더링했으며 메모 하단 잘림을 수정했다. API·DOM 회귀와 CSS 검증을 통과했고 실제 수집·모델 호출·등록·메모 저장은 실행하지 않았다. 변경 화면은 `work/qa_ra_refined/`에 있다.

단계 선택·메모 정렬 및 디자인 분리 수정(2026-10-15, 후속 사용자 피드백): `개발 전략·가교 검토`를 파이프라인 첫 단계로 복원하고 오른쪽 `이전 단계 메모` 드롭다운을 제거했다. 임상 1·2·3상은 그대로 유지한다. 선택한 단계의 표시·메모 제목·목록을 같은 단계 ID로 연결하고, 저장된 선택도 새로고침 후 복원한다. 전체 보기는 단계와 메모 열이 같은 순서·폭으로 배치되어 한 컨테이너에서 함께 가로 스크롤된다. 메인 RA의 카드 구획·버건디 연결선과 16px 본문을 유지하며 자료 수집 디자인을 `/data-manager.css`로 분리했다. 기존 `bridging` 메모·태그·revision·이력은 변경하지 않는다. 격리 PostgreSQL 포함 테스트 14개, 두 DOM 검증, 실제 서비스 GET 검증을 통과했다. 별도 Chrome headless 프로필로 데스크톱/390px 화면을 실제 렌더링하여 7개 단계·메모 열의 위치/폭 차이 0px, 선택 일치, 가로 넘침 없음과 자료 수집 창을 확인했다. API POST는 차단한 상태로 검증했으며 기존 저장 데이터 해시도 일치했다. 렌더링 결과는 `work/qa_ra_stage_sync/`에 있다.

자료 수집 디자인 실제 적용(2026-10-15): 독립 예시 `work/ra-ingestion-first-design.html`의 구성을 메인 RA 상단 `자료 수집·적재` 창에 반영했다. 제품 검색·요청 카드, 실제 상태 기반 4단계 진행 표시, 확인표에서 읽은 문서/기관/임상시험 수, 기관별 문서 표와 출처 필터·원문 링크, 접이식 원본 확인표·이벤트·로그를 제공한다. 예시의 고정 데이터는 사용하지 않고 기존 GET API와 `staged` 확인표를 읽는다. 읽을 수 없는 확인표 수치는 `—`로 표시하며 원본 확인표를 보존한다. `확인표 검토·자료 등록`은 연결된 세션에서 `/status`로 확인표를 보여주고, 사용자가 별도 승인 버튼을 눌러야 기존 해시 검사 뒤 자료 등록이 시작된다. 마지막 요청/세션, 작성 중 텍스트, 오류와 갱신 시 문서 필터·펼침·스크롤을 유지한다. 자연어·후보 선택·계획 시작·승인 API와 5초 GET 폴링은 유지했으며 CSS는 해당 창에만 적용한다. 서버 재시작 없이 메인 화면 새로고침으로 적용된다. DOM 회귀 및 실제 서비스의 GET 전용 DOM 검증을 통과했다(실제 대기 요청 19문서·3기관·1임상시험). 검증에서 실제 수집·모델 호출·등록 승인은 실행하지 않았다. 실제 브라우저 렌더링 검증은 수행하지 않았다.

본문 중심 화면 및 프로젝트 검토 흐름(2026-10-15, 후속 사용자 피드백): 아래 일반 개발 흐름을 대체하여 `품질·분석 → 비임상 → 임상 1상 → 임상 2상 → 임상 3상 → 허가·외삽`으로 정리했다. 단계는 현재 `ra_tasks`의 품질·평가·규제 문서 라우팅, `study_registry`의 임상 시험 식별, `ra_topic_queries`의 PK·유효성·안전성·면역원성 검색 주제에 맞춘 메모 분류이며 필수 시험이나 자동 검색 필터가 아니다. 2상은 사용자 요청으로 명시하며 해당 여부·설계·생략 근거를 메모로 검토한다. 품질·제조 공통 가로줄과 긴 일반 흐름 설명을 제거했다. 헤더 92→60px, 작업 도구줄 80→48px, 중앙 간격 20→10px로 줄이고 답변 14→16px·단계 메모 12→16px로 키웠다. 기존 개발 전략·가교/임상시험 신청/허가 후 관리 메모가 있는 경우에만 작은 `이전 단계 메모` 선택기로 제공하며 내용·태그·revision·이력은 변경하지 않는다. ## 검색과 답변

공통 경로는 질문 해석 → 상품·기관별 검색 계획 → BGE-M3/BM25 → 예산 내 원문 문맥 선택 → 답변 생성 → 원문 인용·조건 검사다. 검색 페이지 수 기본값은 5이며 1~10을 허용한다.

임상 소제목은 원래 source unit의 문자 위치를 보존하며 분리한다. 직접 검색된 표가 연결 문맥과 중복돼도 직접 검색 우선순위를 유지한다. 표를 발췌할 때는 원문 헤더와 필요한 병합 행 전체를 유지하고, 공급되지 않은 원문 구간을 명시한다. 문자 중간에서 잘라 인용하거나 빈 셀을 채우지 않는다.

답변에는 검사한 값과 용량·비교군·분석·시점·투여 경로·간격 등의 원문 조건을 표시한다. 문자·조건 인용 실패 시 같은 근거로 한 번만 교정하며 해당 호출도 사용량에 기록한다. 명시적으로 요청한 조건과 충돌하는 값은 답변에서 제외한다. 인용 검사 통과가 임상 의미나 행·열 귀속의 정확성을 자동 인증하지는 않는다.

## API 성능평가

사용자 지정에 따라 성능평가는 **OpenAI API gpt-4o-mini**를 사용한다. 서비스 기본 답변 제공자는 기존 로컬 Ollama 설정이며 평가 제공자와 구분한다. 가용성 확인 호출, 자동 HTTP 재시도, 무제한 재평가를 하지 않는다. 공개 RA 출처·원본 해시·보류 제외를 확인한 뒤 평가하며, 프로젝트 일일 기록은 다른 계정 사용량을 포함하지 않는다.

~~~powershell
# 공개 출처 감사만 수행: API 호출 없음
.\.venv\Scripts\python.exe -X utf8 -B tmp/public_source_regression.py

# 향후 생성 계약을 변경한 뒤 평가할 때의 예시: 새 해석+답변 최대 2회
.\.venv\Scripts\python.exe -X utf8 -B -m eval.ra3_openai_eval --release data/versions/01_pilot_baseline_2026-10-10/embedded/rag_finalization_2026-10-10_v2 --out data/runs/q012_followup_new --case-id Q012 --max-api-calls 2
~~~

평가는 원문 정답·루브릭을 생성 요청에 넣지 않는다. 검색 페이지 적중, 실제 공급 문맥, 인용 검사, 원문에 따른 답변 판정을 분리해 기록한다. 이번 12개 개발 문항과 실패 문항별 후속 실행은 전체 상품의 임상 일반화나 미노출 문서 성능을 측정하지 않는다. 단계별 코드·응답·호출 수를 고정하고, 서로 다른 코드의 결과를 한 번의 전체 평가 점수로 합치지 않는다.

## CLI

~~~powershell
.\.venv\Scripts\python.exe -X utf8 -B -m rag.pipeline --run data/versions/01_pilot_baseline_2026-10-10/embedded/rag_finalization_2026-10-10_v2 --query "EMA 문서에서 SB17-1001 시험의 투여 용량과 경로는?" --output data/runs/my_rag_answer_001.json
~~~

상품·기관·문서 및 비기본 문서 포함 옵션으로 범위를 제한한다. RA 경로는 질문 결과를 파일에 저장하고 최근 20개를 메모리에 복원한다. 과거 결과도 ID로 조회할 수 있다. 원본 검토 서버는 OCR이나 모델을 실행하지 않는다. 새 문서 처리 절차는 [전처리 워크플로우](../docs/preprocessing/LOCAL_PDF_WORKFLOW.md)를 따른다.


현재 제품별 문서/전체/기본 검색 청크는 SB17 31/3,059/2,702, ABP654 21/2,408/1,779, CTP43 23/2,955/2,507, BMAB1200 10/1,090/917, BAT2206 7/576/430이다. 총 기본 검색 범위는 8,335청크다. BAT2206의 FDA 라벨도 기본 검색으로 공급되며, 상품별 핵심 라벨 질의는 문서 고정 없이 API 평가했다. 9개 보류 문서는 계속 제외한다.

API ID 선택 경로는 원문 헤더·연결 시험 제목·값을 포함한 문장으로 조건을 보충하고, 관계가 없는 표/시험/비교 조건을 차단한다. 표 머리글을 수치 답으로 선택하지 못하게 하고, BMI 복합 단위와 온전한 CI 셀을 보존한다. 명시적인 다중 비교 및 군별 PK 분석집단 인원 요청에 일부만 답한 경우 원문 헤더로 누락을 확인하여 부분 답변으로 표시한다. 최신 회귀는 539개 통과했다. 기본 로컬 Ollama 경로의 실제 답변 성능은 이번 OpenAI 결과로 인증하지 않았다. 단계별 실제 API 사용량은 최신 평가 기록과 `data/runs/model_quota/` 장부에서 확인한다.


마지막 OpenAI 추가 평가는 기존 응답 근거에 없던 승인 문서 6버전을 사용했다. 핵심 사실 원문 확인은 4/6이며 FDA 2문항은 보완이 필요하다. 개발 실패를 수정한 회귀이며 독립 일반화 성능으로 해석하지 않는다. 이후 검사만 재적용해 FDA 통지 내용의 불완전한 항목은 제외하고, 소아 적응증의 잘못된 출처는 보류했다. 현재 검사 코드로 새 답변 생성은 재평가하지 않았다. 실제 사건(시판 통지/라벨 제출)과 허가 대상(소아 적응증/PREA)을 원문으로 구분하며, 관련 검사는 직접 인용 서비스 경로에도 적용한다. 전처리·임베딩 실행 완료와 표/그림 의미 검토 상태는 별도로 유지한다.
