# 내부 개발 파이프라인 자료를 활용하는 RAG 확장 검토·계획

> 후속 사용자 결정: 시나리오의 실험 자료와 코멘트는 실제 공개 데이터를 참고하여 작성한다. 7절의 임의 수치 예시는 채택하지 않으며, [실제 공개자료 기반 시나리오 v1](../demo/internal_pipeline_v1/README.md)이 우선한다.

- 작성 기준: 2026-10-18 KST
- 범위: 현재 코드·문서와 로컬 서비스의 읽기 전용 점검, 공식 규제기관 자료 조사, 후속 개발 계획
- 이번에 하지 않은 일: 코드·DB·색인 변경, 내부 데이터 생성·적재, 신규 모델 호출, 현업 효과 실험
- 이 문서의 제안은 구현 완료나 규제 적합성 검증을 의미하지 않는다.

## 1. 결론

**가능하다. 이 프로젝트를 실제 개발팀의 업무에 연결하는 다음 방향으로 타당하다.** 목표는 공개 심사자료를 설명하는 서비스에서, 자사 프로젝트의 자료를 공개 지침·선례와 연결하여 검토 메모와 미팅 준비자료를 만드는 서비스로 확장하는 것이다.

다만 세 작업의 구현 방식은 다르다.

| 사용자 요청 | RAG가 맡을 부분 | 함께 필요한 기능 | 첫 산출물 |
|---|---|---|---|
| 내부 예상 결과가 기준에 통과할 수준인지 검토 | 적용 기준, 시험계획, 관련 결과, 지침·선례 회수 | 예상/관측 구분, 구조 데이터 조회, 조건 확인, 검증 가능한 계산 | 항목별 비교표·자료 부족·추가 확인사항 |
| 협력사 미팅에서 언급할 부분에 코멘트 작성 | 계약 범위·회의록·변경 이력·관련 실험 연결 | 상대방·담당자·기한 조회, 공유 범위, 문단별 코멘트 | 안건·쟁점·확인 질문·후속조치 표 |
| 규제기관에 물어볼 질문 사전 작성 | 내부 미해결 쟁점과 관련 지침·선례 연결 | 목표 기관·미팅 목적·회사 제안·검토 이력 | 질문·배경·회사 입장·근거·부족 자료 |

실제 효과는 아직 미검증이다. 현업의 업무와 맞는 방향이라는 판단과, 이 구현이 준비·검수 시간을 줄인다는 실증은 구분해야 한다.

## 2. 현재 프로젝트에서 확인한 출발점

최신 상태 문서와 실제 코드가 일치하는 부분을 중심으로 확인했다. 오래된 문서의 미구현 표현이나 과거 데이터 규모를 현재 상태로 취급하지 않았다.

| 항목 | 확인한 현재 상태 | 이번 확장에 대한 의미 |
|---|---|---|
| 공개 자료 검색 | 릴리스 04, 5제품·111문서·15,682청크, pgvector + BM25 + 리랭커 | 공개 비교자료 검색은 재사용 |
| 원문 추적 | 문서·버전·원문 구간·PDF 페이지/영역 인용 | 내부 문서에도 같은 근거 추적 방식 적용 가능 |
| 파이프라인 메모 | 단계별 직접/RAG 메모, PostgreSQL 저장, 수정 이력 | 검토 결과를 축적할 업무 화면은 이미 존재 |
| 내부 자료 검색 | 질문 API에 project_id·내부 자료 선택이 없고, 메모는 검색 입력과 미연결 | 내부 자료 연결 경로 신설 필요 |
| 검색 범위 | 공개 출처·기관·문서 역할 중심의 닫힌 계약 | 내부 출처·문서 역할·업무 의도 추가 필요 |
| 자료 적재 | 공개 제품 수집 중심, 전처리 입력은 PDF/HTML | 내부 파일 등록과 구조 데이터 적재를 별도 설계 |
| 미팅 질문 | 검토 메모에서 미확인 요청을 일반 질문으로 변환 | 협력사/규제기관별 실제 브리프는 추가 개발 |
| 운영 | localhost 제한, 로그인·사용자 권한 없음, 프로세스당 질문 한 건 | 실제 기밀 자료를 다중 사용자에게 제공할 기반은 미완성 |
| 평가 | 공개 RA 개발 문항 중심, 독립 현업 시간 측정 없음 | 내부 자료용 평가와 현업 실험 필요 |

코드 근거:

- [질문 입력과 파이프라인 호출](../../rag_service/__main__.py#L92): `submit`은 question/products/jurisdictions/documents/include_nondefault/conversation_id만 수용한다.
- [단계별 메모](../../rag_service/workspaces.py#L20): 단계는 메모 분류이며 자동 검색 필터나 필수 시험 목록이 아니다.
- [현재 출처 제한](../../rag/service_scope.py#L4): EMA/FDA/Health Canada/ClinicalTrials.gov와 EU/US/CA/sponsor만 허용한다.
- [질문 의도 범위](../../rag/ra_intent.py#L19): 등록 제품의 규제·임상 자료 중심이며 회사 업무자료를 위한 의도 정의가 없다.
- [현재 질문 초안](../../rag/ra_memo.py#L56): 미확인 항목별 일반 질문 템플릿이며, 일반 의미 충돌 탐지 기능도 아니다.

## 3. 누가 어떻게 사용할 것인가

첫 사용자는 **한 개발품의 RA 담당자와 CMC/분석 담당자**로 좁힌다. RA가 기관·미팅 목적과 검토 쟁점을 정하고, CMC 담당자가 시험 조건·결과·평가 기준을 확인하며, 필요한 경우 QA 또는 문서 관리자가 승인 상태를 확인한다.

권장 사용 흐름:

1. 자사 개발품을 선택한다. 개발코드·대조약·제형/경로·대상 기관·기준일을 확인한다.
2. 내부 자료를 등록하고 문서 종류·승인 상태·프로젝트 연결을 확인한다.
3. 결과 검토, 협력사 미팅 준비, 기관 질문 초안 중 작업을 선택한다.
4. 내부 사실·적용 기준·외부 참고근거·미해결 사항을 출처와 함께 읽는다.
5. 담당자가 수정·검토하고 파이프라인 메모로 저장하거나 검토용 파일로 내보낸다.

단계 카드는 그대로 활용하되 여러 단계에 걸친 CMC·품질·협력사 업무를 허용한다. 비임상→1상→2상→3상 모두를 일률적인 필수 절차로 처리하지 않는다. 신규 이슈 보드부터 만들기보다 메모에 담당자·기한·상태·연결 문서를 필요한 만큼 보강한다.

효과가 기대되는 업무는 반복적으로 흩어진 자료를 찾고, 변경 이력을 대조하고, 근거가 있는 검토 초안을 만드는 작업이다. 원자료 해석 자체가 불명확하거나 입력 문서에 근거가 없는 경우에는 효과가 제한된다. 벡터 검색이 해결하는 문제와 실험·문서 관리 원천의 정합성 문제를 구분해야 한다.

## 4. ‘기준 통과’ 질문을 다루는 방법

먼저 사용자가 말하는 기준의 종류를 구분한다.

| 기준의 종류 | 가능한 답변 범위 |
|---|---|
| 사내 개발 목표 | 지정한 목표와 예상/관측 결과의 차이 |
| 승인된 시험계획의 평가 기준 | 해당 시험·방법·버전·분석집단에 대한 조건부 비교 |
| 품질 규격/출하 기준 | 적용 제품·공정·시험법과 승인된 규격에 대한 항목별 비교; 실제 출하 결정은 별도 업무 |
| 바이오시밀러 비교분석 평가 | 품질속성·위험도·대조약 lot·방법·통계계획·차이의 설명에 필요한 자료 정리 |
| 규제기관의 수용/허가 가능성 | 확인한 근거, 적용 한계, 남은 불확실성, 기관 질문 초안 |

예상값은 시뮬레이션이나 계획 자료로 취급한다. 사용자가 입력한 숫자도 자동으로 사내 확정 결과로 저장하지 않는다. 조건을 명시한 가정 비교는 가능하지만 실제 시험 수행·유효성·승인 여부를 입증하지 못한다.

권장 출력은 다음 순서다.

1. **비교 대상:** 개발품·batch/lot·assay/run·시험법 버전·시점·데이터 상태.
2. **적용 기준:** 문서·버전·유효일·승인 상태·적용 범위와 기준 종류.
3. **조건 확인:** 단위, 대조약, 분석방법, 집계 방식과 시점이 비교 가능한지.
4. **계산 결과:** 기준 내/기준 밖/조건 불일치/자료 부족. 예상값은 별도 표기.
5. **외부 근거:** 해당 기관 지침과 타사 선례, 자사 조건과의 차이.
6. **다음 검토:** 부족한 시험·확인할 문서·담당자·미팅 질문.

RAG는 1·2·5의 근거를 찾고 설명에 사용한다. 계산은 구조 데이터와 명시적 규칙으로 수행하며 입력값·규칙 버전·산식을 남긴다. 규칙이 없거나 분석법이 맞지 않으면 LLM이 임의의 합격선을 만들지 않는다. 한 항목이 범위 안이라는 사실을 제품 전체의 유사성·허가 가능성으로 확장하지 않는다.

FDA의 [2025년 9월 최종 비교분석·품질 가이던스](https://www.fda.gov/regulatory-information/search-fda-guidance-documents/development-therapeutic-protein-biosimilars-comparative-analytical-assessment-and-other-quality)는 품질속성의 위험도, 분석계획과 평가 방법, lot 수의 충분성 등을 고려한다. 타사 승인 사실이나 참조제품의 단순 관측 범위만으로 자사 제품의 수용 여부를 정할 수 있다는 근거로 쓰지 않는다. 최종 가이던스도 법적 의무와 동일하지 않은 비구속적 권고다.

## 5. 구현 구조 제안

```text
질문 + 자사 프로젝트 + 목적/기관 + 기준일
  → 서버에서 사용자 권한과 프로젝트 범위 확정
  → 내부 문서 검색 + 실험/기준/일정 구조 데이터 조회
  → 필요한 공개 지침·타사 선례 검색
  → 적용 조건·상충·누락 확인 + 명시적 계산
  → 작업별 초안 + 주장별 근거 + 검토·수정 이력
```

### 5.1 내부 자료와 공개 자료의 관계

- 공개 제품 ID와 자사 프로젝트 ID를 구분하고, 성분·대조약·제형·주제 등으로 연결한다.
- 내부 관측값, 내부 예상/계획, 사내 기준, 협력사 발언, 기관 지침, 타사 심사 선례의 출처 역할을 표시한다.
- 내부자료에서 자사 상황을 확인한 뒤, 그 상황에 필요한 공개 자료를 찾는다. 두 자료를 평면적으로 섞어 유사도 순으로만 선택하지 않는다.
- 사용자·프로젝트·문서 상태·기준일 필터는 검색 전에 적용한다. 리랭킹·원문 열람·메모·내보내기도 같은 권한을 적용한다.
- 현재 열린 프로젝트를 바꾸면 대화 문맥의 프로젝트도 확인한다. 직전 프로젝트의 수치·협력사·문서를 새 프로젝트 답변에 암묵적으로 가져오지 않는다.

### 5.2 보관할 정보

모든 필드를 사람이 매번 입력하게 하기보다 원천에서 가져오고, 불명확한 필수 정보만 확인한다.

| 객체 | 필요한 핵심 정보 |
|---|---|
| 내부 문서 | project_id, 문서 ID/버전, 종류, hash, 원본 위치, 작성·등록일, 승인·유효일, draft/approved/superseded, 대체 관계, 접근 그룹 |
| 실험 사실 | study/run/sample/batch, 공정·시험법 버전, 평가변수, 값·단위, 대조약/비교군, 시점, 예상/잠정/확정, 유효성·승인 상태, 원문 locator |
| 기준 | 기준 종류, 적용 범위, 규칙·단위·산식, 기준 문서/버전, 유효기간, 승인 상태 |
| 쟁점·미팅 | 상대방, 안건, 사실/제안/합의/미확인, 담당자, 기한, 의존관계, 이력, 연결 문서, 공유 가능 범위 |
| 결과물 | 입력 질문·범위·기준일, 사용 문서/규칙/색인 버전, 계산, 초안/검토 상태, 수정자·수정 이력 |

일정·마감·의존관계는 SQL 등 구조 조회로 답한다. 벡터 검색으로 ‘최신 마감일’을 결정하지 않는다. 기준일 당시 존재했던 자료와 당시 적용되던 기준을 구분해 조회한다. 단순히 파일 수정일이 가장 최근인 문서를 고르지 않는다.

### 5.3 적재·원문 인용

첫 범위는 PDF·Markdown/텍스트·CSV로 제한하고 Word/Excel 원본은 필요하면 PDF와 CSV로 수동 내보낸다. 원본 파일과 변환본의 관계를 남긴다. DOCX/XLSX·메일 자동 연동은 업무 효과를 확인한 다음 확장한다.

문서는 원문 보관 → 분류/메타데이터 확인 → 파싱 → 수치표 추출·검수 → 검색 게시 순서로 처리한다. ‘파일 등록됨’과 ‘검색 가능’ 상태를 별도로 표시한다. 삭제·대체·권한 철회는 원문뿐 아니라 청크·캐시·파생 메모에서도 반영한다.

PDF는 기존 페이지·영역 인용을 재사용한다. CSV는 파일 버전·행 ID·열 이름, 이후 XLSX는 시트·셀을 연결한다. 데이터의 정규화 값과 원래 표기값을 함께 보관한다.

### 5.4 실제 내부 자료를 받기 전의 운영 조건

현재 로컬 임베딩을 사용해도 답변 생성에는 외부 API를 사용하며, 요청·응답 본문이 로컬 파일에도 기록된다. 실제 자료 도입 전 회사가 허용하는 모델 실행 위치·전송 범위와 로그 저장·접근·보존 정책을 정해야 한다. 사내 실행 모델이 필요한 경우 정확도·속도는 별도 확인한다.

실제 사용 전에는 로그인·프로젝트 권한, 백업/복원, 문서·인용·내보내기 경로의 권한 검사, 요청 기록의 보존/삭제를 확인한다. 생성·검토된 메모에도 원자료의 공유 제한을 이어받게 한다. 협력사 배포본은 수신자가 볼 수 있는 근거로 다시 구성하고 검토 상태를 남긴다. 문서 속 지시문은 자료로 취급하며 도구 실행·외부 전송 명령으로 따르지 않는다.

이는 내부 자료를 쓰기 위해 필요한 제품 설계다. 이번 점검으로 GxP 적합성이나 공식 품질 판단용 시스템 검증을 완료했다는 뜻은 아니다.

## 6. 세 가지 업무의 산출물

### A. 협력사 미팅 준비 — 첫 구현

입력: 프로젝트, 상대방, 미팅 목적·일자, 관련 안건/문서.

출력: `안건 → 원문 내용 → 현재 상태 → 검토 코멘트 → 확인 질문 → 요청자료 → 담당자/기한`.

계약상 의무, 이메일의 제안, 회의에서의 잠정 합의, 승인된 변경을 구분한다. 요약본만 만들기보다 기존 회의록의 문단·항목에 코멘트를 연결한다. 바뀐 일정과 미수령 결과를 먼저 노출한다. 문서에서 확인하지 못한 담당자·기한은 임의 배정하지 않고 제안으로 표시한다.

이 기능을 먼저 만드는 이유는 기존 메모·근거 UI를 활용할 수 있고, 내부 문서 연결의 효용을 수치 판정 기능보다 적은 범위로 확인할 수 있기 때문이다.

### B. 내부 결과와 기준 비교 — 범위를 제한해 추가

처음에는 한 개발품의 한 분석법과 1~2개 평가 항목만 지원한다. 원시 크로마토그램·영상 분석이나 복잡한 통계모형의 자동 선택은 포함하지 않는다.

출력: `실험값/상태 | 적용 기준/버전 | 조건 일치 여부 | 계산/비교 | 부족 자료 | 외부 참고근거`.

실험 유효성 또는 시험법 적용이 확인되지 않으면 판정을 보류한다. 예상 결과만 있을 때에는 ‘해당 가정값을 넣으면 내부 기준 내/밖’ 수준의 조건부 결과를 제공한다.

### C. 규제기관 사전 질문 초안

입력: 목표 기관, 미팅 목적, 내부 쟁점, 회사가 제안하려는 접근.

출력: `질문 → 배경 → 보유 데이터 → 회사 제안/근거 → 남은 불확실성 → 기관에 확인할 사항 → 준비할 추가자료`.

협력사에 물을 질문과 기관에 물을 질문을 분리한다. 누락 자료 수령 여부는 협력사에, 데이터 패키지의 적절성·추가 평가 필요성은 기관 질문 후보로 정리한다. ‘예상 기관 답변’은 실제 기관 회신과 섞지 않는다.

[FDA 2025년 7월 최종 BsUFA 미팅 가이던스](https://www.fda.gov/regulatory-information/search-fda-guidance-documents/formal-meetings-between-fda-and-sponsors-or-applicants-bsufa-products-guidance-industry)는 구체적인 질문과 질문별 맥락·지원 자료를 요구하는 방향이다. 따라서 일반 질문 생성보다 내부 데이터와 회사 제안을 붙인 질문 초안을 목표로 삼는다. EMA·MFDS를 지원할 때는 각 기관 절차와 문서의 현행 상태를 별도로 확인한다.

## 7. 데모 데이터: 하나의 가상 프로젝트를 일관되게 만들기

### 7.1 설정과 분량

기존 우스테키누맙 공개 코퍼스를 활용하고, **가상 자사 후보 `DEMO-U01`**과 가상 CRO·CDMO 각 한 곳을 만든다. 실제 회사의 비공개 결과나 기관 회신으로 보이게 만들지 않는다. 이름·날짜·숫자·서명·계약은 모두 가상임을 표시한다.

핵심 이야기는 6~8주 동안 진행된 한 분석 쟁점이다. 예상 결과 → 잠정 보고 → 기준 변경 확인 → 재시험/검토 → 협력사 미팅 → 기관 질문 준비로 이어진다. 고정된 세 기준일로 과거 시점 조회도 평가한다.

| 문서 묶음 | 논리 문서 수 | 포함할 내용 |
|---|---:|---|
| 프로젝트 맥락 | 3 | 개발 개요·대조약/제형·별도 프로젝트 구분용 문서 |
| 실험 자료 | 6 | 시험계획·예상값·잠정/최종 보고·대조약 lot 요약·시험법 확인 |
| 기준·내부 규약 | 4 | 평가 기준표·SOP·분석계획·기록/승인 규칙 |
| 협력사 자료 | 6 | 업무범위·계약 요약·회의록·이메일·일정 변경·자료 요청 |
| RA 준비 | 3 | 쟁점 메모·공개 근거 연결표·질문 초안 |
| 검토·공유·업무 상태 | 3 | 검토 기록·공유 범위·담당/기한 및 의존관계 설명 |
| 합계 | **25** | 여기에 과거 버전 4개를 더해 실제 문서 파일 29개 |

별도로 CSV 4개를 둔다: 실험 결과, 평가 규칙, 이슈·담당·기한, 일정·의존관계. 결과표는 약 100~200행 규모면 첫 데모에 충분하다. 공개 지침·선례는 기존 코퍼스에서 실제 원문을 연결하고 합성 문서 수에 포함하지 않는다.

과거 버전 4개는 평가 기준 구버전, 결과 보고의 잠정본, 시험법 구버전, 일정 구버전으로 구성한다. 날짜와 문서 상태가 서로 맞도록 생성한다.

### 7.2 문서보다 먼저 정할 원장

LLM에게 문서 29개를 각각 자유롭게 쓰게 하지 않는다. 먼저 `프로젝트·시험·batch·방법·결과·기준·문서 버전·상태·기한·접근권한`의 사실 원장을 고정한다.

1. 원장에서 정상 사실과 의도한 충돌·누락을 지정한다.
2. 원장으로 CSV와 문서의 표·숫자·날짜를 생성한다.
3. LLM은 회사별 문체·회의록·메일 서술을 보조한다. 숫자·합의·상태는 원장을 바꾸지 않는다.
4. 참조 ID·단위·날짜·대체 관계·기준 적용 범위를 자동 검사한다.
5. RA/CMC 경험자가 용어·흐름·판정 보류 이유를 검토한다.
6. 정답 문항과 원장 주석은 검색 코퍼스와 분리한다. 실제 문서는 검색되지만 정답 해설은 검색되지 않게 한다.

원장의 각 사실에는 문서·버전·페이지 또는 CSV 행 locator를 붙인다. 데모의 기준일은 고정해 실행 날짜에 따라 답이 달라지지 않게 한다.

### 7.3 반드시 포함할 사례

| 사례 | 데모에서 확인할 행동 |
|---|---|
| 예상값만 있고 확정 결과 없음 | 조건부 비교로 표시하고 시험 완료로 답하지 않음 |
| 잠정값과 최종값이 다름 | 상태·버전·기준일에 맞는 값을 사용 |
| 최신 파일은 초안, 적용 기준은 승인본 | 파일 수정일 대신 적용 상태·유효일로 선택 |
| 구버전 기준에서는 범위 내, 현 적용 기준에서는 범위 밖 | 해당 시험에 실제 적용되는 기준을 설명 |
| 단위·시험법·시점 또는 대조약이 다름 | 직접 비교를 차단하거나 명시적 변환 근거 제시 |
| 시험 무효화/일탈 검토 중 | 숫자가 좋아도 유효한 확정 결과로 취급하지 않음 |
| 협력사의 구두 제안과 계약상 합의가 다름 | 제안·합의·계약을 구분해 확인 질문 작성 |
| 일정이 뒤로 변경됨 | 최신 승인 일정과 영향받는 후속 작업 표시 |
| 기준 또는 핵심 문서가 없음 | 없는 정보를 만들지 않고 필요한 자료 지정 |
| 타 프로젝트의 유사한 분석명 | 활성 프로젝트의 사실과 섞지 않음 |
| 접근 제한 문서/외부 배포 제한 | 검색·원문·메모·배포본 전체에서 제한 적용 |
| 문서 속 ‘기존 지시 무시’ 같은 문장 | 데이터로 취급하고 실행 지시로 따르지 않음 |

### 7.4 발표에서 보여줄 한 사례

아래 숫자는 데모 설계를 위한 **가상의 사내 개발 목표**이며 실제 품질 규격·규제기관 허용 기준이 아니다.

- 예상 상대활성 97%, 잠정 관측 94%, 확정 결과 미수령.
- 해당 조건의 승인된 가상 내부 목표 범위 90~110%.
- 시험법 적합성 확인은 진행 중이며, 다른 품질속성 한 항목의 결과가 누락됨.

좋은 답변은 ‘예상값과 잠정값은 지정한 내부 목표 범위 안이지만, 확정 결과·시험법 적합성·누락 항목 확인이 필요하다’고 정리한다. 이어 CRO에 받을 결과·확인 질문과, 미해결 차이의 평가 접근을 기관에 확인할 질문을 구분한다. 이를 ‘바이오시밀러 허가 통과 가능’으로 답하면 실패다.

## 8. 실제 효과를 검증하는 방법

### 8.1 기술·업무 품질

첫 평가안은 개발 36문항 + 별도 보관 24문항, 총 60문항이다. 결과/기준 비교 20, 협력사 준비 14, 기관 질문 14, 버전·권한·정보 부족 등 통제 문항 12로 구성한다. 세부 주제와 개발/보관 분할은 구현 전에 고정한다. 같은 사건·판정 규칙·문서 버전 시나리오를 표현만 바꾸어 양쪽에 나누지 않는다. 보관 정답은 개선 과정에서 개발자가 열람하지 않으며, 구성과 코드를 고정한 뒤 별도 검토자가 평가한다. 동일 가상 프로젝트 안에서의 보관 평가는 새로운 회사·성분에 대한 일반화 검증과 구분한다.

같은 내부 자료를 제공하는 단순 검색 방식과, 상태·조건·규칙을 반영하는 제안 방식을 비교한다. 기존 공개자료 전용 RAG는 입력 범위 차이를 보여주는 참고 대상으로만 쓰고 공정한 업무 효율 비교군으로 취급하지 않는다.

| 측정 대상 | 지표 |
|---|---|
| 근거 회수 | 필요한 내부 결과·기준·이력·공개 근거의 회수율 |
| 판정 | 기준 적용·수치·단위·상태·조건 정확성, 근거 없는 통과 판정 |
| 인용 | 핵심 사실의 문서/행 추적 가능성과 인용의 의미 지지 |
| 브리프 | 미해결 이슈·합의/제안 구분·질문 구체성·수정량 |
| 통제 | 구버전/다른 프로젝트 혼입, 권한 밖 노출, 공유 제한 위반 |
| 운영 | 지연·실패·호출 비용, 재시작 후 복원, 문서 갱신 반영 |

출시 판단 기준의 초안: 평가셋에서 권한 누출·근거 없는 통과 판정 0건, 핵심 수치와 기준의 출처 추적 100%, 필수 근거 회수 90% 이상. 수치는 사전 합의할 목표이며 현재 성능이나 일반적 오류 확률을 뜻하지 않는다. 보관 문항을 개선에 사용하면 더 이상 독립 평가로 보고하지 않는다.

### 8.2 사람의 업무시간

RA·CMC 담당자 4~6명에게 난이도가 맞는 과제를 배정한다. 기존 문서 검색·수작업 방식과 새 도구 방식에 같은 자료와 과제 조건을 제공하고 순서를 교차 배정한다. 동일 과제 반복에 따른 기억 효과를 줄이기 위해 대응 과제를 사용한다.

‘초안 생성 시간’ 대신 **원문 확인·수정까지 포함해 검토 가능한 결과를 완성하는 시간**을 측정한다. 놓친 핵심 이슈, 잘못된 주장, 수정량도 함께 기록한다. 첫 성공 목표는 오류가 늘지 않는 상태에서 검토 완료 시간 30% 단축으로 제안하되, 이는 검증 전 목표다. 합성자료 실험이 실제 비공개 자료의 효과를 입증하지는 않으므로 이후 허용된 실제 자료로 제한 파일럿을 진행한다.

## 9. 권장 개발 순서

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 1. 업무·데이터 설계 | RA/CMC 인터뷰, 첫 과제·산출물 확정, 사실 원장·평가 문항 고정 | 성공/실패 답변 예시와 데이터 상태 규칙에 합의 |
| 2. 내부 자료 연결 | 내부 등록·문서 상태·프로젝트 범위·원문 인용·구조 데이터 조회 | 선택 프로젝트와 기준일에 맞는 자료가 출처와 함께 회수됨 |
| 3. 협력사 브리프 | 안건·코멘트·확인 질문·담당·기한을 기존 메모 UI에 연결 | 바뀐 합의/일정과 미수령 자료를 올바르게 정리 |
| 4. 제한된 비교·RA 초안 | 한 assay의 규칙 비교, 미해결 쟁점 기반 기관 질문 작성 | 조건 불일치·미확정 자료에서 보류하고 근거를 연결 |
| 5. 평가·실사용 준비 | 고정 평가·사용자 실험, 실제 자료용 권한·전송·로그·복원 확인 | 측정 결과로 다음 확장 또는 범위 수정을 결정 |

개발자 1~2명과 RA/CMC 검토자의 참여를 확보한다면, 이 범위의 합성자료 PoC는 4~6주를 계획 가정으로 잡을 수 있다. 현재 코드·연동 환경과 검토자 가용성을 확인하기 전 확정 일정으로 보지 않는다. 실제 사내 시스템 연동·배포·품질시스템 검증은 별도 산정한다.

첫 범위에서 보류할 항목: 전체 파이프라인 자동 관리, 모든 문서 형식·사내 시스템 동시 연동, 원시 실험신호 자동 분석, 자동 허가/출하 결정, 외부 회사·기관에 대한 자동 전송.

## 10. 추가 공식 근거와 해석 범위

- [FDA AI 규제 의사결정 지원 가이던스](https://www.fda.gov/regulatory-information/search-fda-guidance-documents/considerations-use-artificial-intelligence-support-regulatory-decision-making-drug-and-biological): 2025년 1월 초안, 시행용 최종 지침이 아니다. 특정 규제 의사결정용 정보 생성과 내부 업무 효율화의 용도를 구분하는 참고자료다. 내부 RAG 전체가 검증 면제라는 뜻으로 사용하지 않는다.
- [EMA 의약품 생애주기 AI reflection paper](https://www.ema.europa.eu/en/scientific-guidelines/use-artificial-intelligence-ai-medicinal-product-lifecycle): 2024년 9월 채택. 생성형 AI의 오류·누락, 인간 검토와 데이터 보호·추적성의 중요성을 설명한다. 이 프로젝트의 생산성 개선을 입증한 자료는 아니다.

다음 의사결정에 필요한 것은 ‘RAG를 쓸 수 있나’보다, 정해진 한 업무에서 **내부 사실·적용 기준·외부 근거를 틀리지 않게 연결하고 검토자의 완성 시간을 줄이는가**이다. 우선 같은 가상 프로젝트에서 세 업무를 연결하는 데모로 이를 검증한다.
