# 저장 메모 구조화와 시나리오 업무 재사용 검토

- 기준: 2026-10-18 KST
- 방법: 실제 8885 서비스의 GET /api/projects·프로젝트 상세·저장 보고서, 저장/렌더링 코드 확인
- 변경 범위: 검토 문서와 합성 초안만 작성. 기존 메모·DB·서비스 코드는 변경하지 않음

## 1. 핵심 판단

사용자가 지적한 정돈이 먼저 필요하다. 다만 ‘실험 / 의견 / 결과’를 같은 수준의 분류로 저장하면 서로 겹친다. **실험·시험·쟁점은 묶음의 대상이고, 결과·기준·의견·결정·할 일·질문은 그 대상에 붙는 정보 종류**로 나누는 편이 적합하다.

메모의 긴 본문을 보기 좋게 나누는 작업과, 시나리오 업무에 재사용할 수 있는 정보를 저장하는 작업을 함께 해야 한다. 태그만 추가하거나 제목만 나누면 후속 업무는 다시 본문 전체를 해석해야 한다.

## 2. 직접 확인한 현재 상태

현재 프로젝트 1개에 활성 메모 3개, 보관 메모 3개가 있다. 활성 메모는 모두 `source.kind=answer`, 즉 답변 전체 저장이며 태그는 비어 있다.

| 활성 메모 | 현재 한 본문에 포함된 내용 | 필요한 묶음 |
|---|---|---|
| CT-P43 프로토콜과 EMA 최종 심사 비교 | 계획, 실제 수행·평가, 기관 판단, 두 문서 차이에 대한 해석, 미확인 항목 | 시험·평가변수·문서 버전별 계획/결과/해석/질문 |
| Steqeyma 보관 조건 | 서로 다른 제형·상태의 보관 내용 | 제형·희석 여부·보관 조건별 사실 |
| SB17 시험대상자 관련 기관별 언급 | SB17-1001/3001, EU/US/CA, 선정·제외 기준, FAS/PPS | 시험 → 대상/분석집단 → 기관·문서별 기준/사실 |

이는 현재 저장 결과의 구성 확인이다. 저장된 답변의 과학적·규제적 정확성을 이번에 다시 인증한 것은 아니다.

원래 RAG 보고서에는 이미 `claims[]`가 있다. 활성 ‘기관별 SB17 시험대상자’ 메모의 원 보고서는 13개 claim을 갖고 `kind`, `task_ids`, `products`, `sources`, `support_review`를 보존한다. CT-P43 메모의 원 보고서는 8개, Steqeyma 메모의 원 보고서는 2개다. 따라서 구조화를 전부 새 LLM 추출부터 시작할 필요는 없다. 이 23개 claim 중에는 여러 시험·조건을 함께 기술한 항목도 있으므로 최종 정보 단위 수와 같지는 않다.

확인된 손실 지점:

1. [workspaces.py:390](../../rag_service/workspaces.py#L390): 단일 claim을 저장할 때 text와 sources를 가져오지만 kind·task_ids·검토 정보를 함께 보존하지 않는다.
2. [workspaces.py:395](../../rag_service/workspaces.py#L395): 전체 답변 저장은 본문 문자열과 모든 claim의 sources를 평탄화한다. 원래 claim별 관계가 메모 스냅샷에서 사라진다.
3. [pipeline-notes.js:71](../../rag_service/web/pipeline-notes.js#L71): 상세 화면은 memo.body 전체를 한 본문 요소로 표시한다.
4. [pipeline-notes.js:94](../../rag_service/web/pipeline-notes.js#L94): 편집도 본문 textarea·단계·태그 중심이다.
5. [app.js:70](../../rag_service/web/app.js#L70): 쟁점별 검토 메모 안에는 이미 claim 단위 저장 버튼이 있다. 메인 답변에는 전체 저장 버튼이 더 눈에 띄는 흐름이다.

기존 `source` 객체에는 원래 본문·인용·문서 버전·보고서 해시가 남아 있다. 재사용 가치가 큰 기반이다. 그러나 `source.kind=answer/claim/evidence`는 저장 방식이며, 결과/의견 같은 업무 내용의 유형은 아니다.

## 3. 최소한의 정보 구조

```text
프로젝트
 └─ 단계 / 실험·시험 / 쟁점 / 미팅
      ├─ 사실·결과
      ├─ 적용 기준
      ├─ 의견·해석
      ├─ 결정
      ├─ 후속 조치
      └─ 미해결 질문

각 항목 → 원문 문서·버전·구간 + 작성/발언 주체 + 상태 + 관련 항목
```

모든 항목을 실험에 억지로 연결하지 않는다. 계약·납기·기관 미팅은 프로젝트·쟁점·미팅 자체에 연결할 수 있다. 실험이 있으면 실험 ID를 연결한다.

### 정보 종류: 우선 여섯 가지

| 유형 | 의미 | 데모 예 |
|---|---|---|
| 사실·결과 `fact` | 관측, 예상, 계획, 문서/업무 사건 | SB17 IV vial FcRn 결합 활성의 공개 보고 범위; 자료가 접수됨 |
| 적용 기준 `criterion` | 적용 조건이 있는 목표·평가 규칙·참고 사례의 비교 범위 | 해당 공개 사례의 assay·제형별 similarity range; 자사 적용 기준과 구별 |
| 의견·해석 `interpretation` | 원자료 해석·가설·검토 의견 | 분석법 영향 가능성을 추가로 확인하자는 연구자 의견 |
| 결정 `decision` | 누가 무엇을 결정했는지 | 검토팀이 추가자료 확인을 결정함; 실제 기록이 없으면 제안으로 유지 |
| 후속 조치 `action` | 담당·기한·완료 조건이 있는 작업 | 기능시험·제형별 결과의 근거 위치 확인 요청 |
| 미해결 질문 `question` | 확인이 필요한 사항 | 시험법 차이의 영향을 배제할 근거가 있는가 |

계획·예상·관측을 `fact`의 modality로 구분한다. 화면에서는 ‘계획’, ‘예상’, ‘결과’로 나눠 보여줄 수 있다. 수치 결과가 많은 경우 `fact`에 measurement 구조를 추가한다. 관측 범위·평균·개별 측정값·비교 범위는 별도 수치 종류로 둔다. 참고 사례의 similarity range를 자사의 승인된 규격으로 바꾸지 않는다. 문장 한 개에 다른 실험·조건·시점이 있으면 더 나누되, 숫자·단위·조건을 떼어 의미가 사라지는 조각을 만들지 않는다.

### 내용 유형과 별도로 보존할 축

| 축 | 예 |
|---|---|
| 대상 | project_id, experiment_id, run_id, issue_id, meeting_id |
| 표현의 주체 | 내부 연구자, 협력사, 신청자, 기관, AI |
| 데이터 성격 | predicted / planned / observed / reported_event / proposal |
| 데이터 성숙도 | preliminary / final / not_applicable |
| 실험 유효성 | pending / valid / invalid / not_applicable |
| 문서 상태 | draft / approved / superseded; 승인 주체·승인일·유효일 |
| 검토 상태 | unreviewed / reviewed / needs_work; 검토자·범위 |
| 시간 | 사건 발생일, 자료 등록일, 적용 시작·종료일 |
| 근거·이력 | document_id, version_id, section/span/row, 원 보고서/claim, 원문 해시 |

승인된 예상 보고서는 여전히 예상 자료다. CRO가 확정한 보고서와 자사 검토 완료도 다르다. 한 개의 ‘확정’이나 ‘신뢰도’ 필드로 이 상태들을 합치지 않는다. 유효성·일정 변경은 변경을 알게 된 시각과 적용 시각을 가진 이력으로 남긴다. 나중에 확인한 상태를 과거 시점 조회에서 미리 사용하지 않는다. 현재 SB17 공개자료 재구성 시나리오에는 실제로 확인되지 않은 run 무효화나 재시험 사건을 만들어 넣지 않는다.

기존 `source_fact/applicant_position/regulator_position/interpretation`은 발언·근거 역할로 보존한다. 이를 위 여섯 가지 업무 유형과 기계적으로 일대일 대응하지 않는다. 예컨대 기관 보고서에 실린 신청자 제안은 자사의 승인된 결정이 아니다.

## 4. 세 업무는 같은 항목을 다르게 조립

| 업무 | 포함·정렬할 항목 | 결과물 |
|---|---|---|
| 결과 검토 | 실험 조건 → 적용 기준 → 사용 가능한 결과 → 관련 의견 → 무효/누락 상태 → 질문 | 항목별 비교표와 판정 보류 이유 |
| 협력사 미팅 | 상대 발언·계약 범위 → 관련 사실 → 결정 → 쟁점 → 제안 코멘트 → 담당·기한 | 안건별 코멘트와 확인 질문 |
| 기관 미팅 준비 | 미해결 쟁점 → 내부 입장 → 보유 결과·한계 → 관련 실제 공개 근거 → 질문 | 회사가 기관에 확인할 질문, 기관에서 받을 것으로 예상하는 질문과 답변 준비 |

구조화된 메모를 그대로 이어 붙여 다시 긴 문장으로 만드는 방식은 피한다. 대상·기준일·자료 상태·공유 범위를 먼저 제한하고, 필요한 항목을 조립한 뒤 근거를 확인한다. 새로 생성한 코멘트나 기관 질문에는 ‘AI 제안’ 상태를 붙인다. 기관에서 받을 것으로 예상한 질문은 실제 접수 질의·기관 입장과 분리하며, 예상 질문마다 답변에 쓸 자료·미확보 자료를 연결한다.

## 5. 원문과 메모의 관계

원문 자료와 그 자료를 해석한 메모는 두 층으로 관리한다.

- 실험값의 근거는 결과표·보고서의 해당 위치다.
- ‘연구자가 시험법 영향을 의심했다’는 사실의 근거는 연구자의 의견 문서다. 해당 문서는 시험법이 원인이었다는 증거가 아니다.
- 재시험을 결정했다는 근거는 결정 기록이다. 이 결정이 기존 결과를 무효화했다는 의미인지도 명시된 범위로 확인한다.
- AI 메모를 다시 검색하더라도 원문으로 이어지는 링크를 유지하고 별도 독립 근거로 세지 않는다.
- 사람이 AI 메모를 검토했다고 메모에 포함된 예상값이 실제 관측값으로 바뀌지 않는다.
- 같은 원문을 인용한 메모가 여러 개여도 증거 수를 부풀리지 않는다. 반대 근거와 조건이 다른 결과는 중복이라는 이유로 합치지 않는다.

현재 E1·E2 같은 인용 ID는 보고서마다 재사용된다. 전역 ID로 사용하지 않고 문서 ID·버전·원문 구간에 연결한다. 원문의 근거와 메모의 derived_from 관계를 분리해 순환 인용을 막는다.

## 6. 저장과 화면의 권장 변화

### 답변을 읽을 때

기존 답변·원문 화면을 유지하면서 짧은 요약 아래에 ‘항목별 정리’를 기본으로 제공한다. 대상별로 묶고 그 안에서 여섯 가지 유형·상태를 표시한다. 자세한 원래 답변은 접어서 열어볼 수 있다.

### 저장할 때

‘답변 전체 저장’은 원문 답변 보관 기능으로 남긴다. 실무 재사용의 기본은 ‘선택 항목 저장’으로 바꾼다.

각 항목은 내용·대상·유형·주체·자료 상태·출처를 미리 채운다. 사용자는 틀린 분류나 불명확한 대상만 확인한다. 자유 의견은 근거 사실을 덮어쓰지 않고 별도 의견 항목으로 추가한다. 유형을 고쳤다는 사실과 내용을 바꿨다는 사실도 이력에 남긴다.

### 저장된 메모를 볼 때

단계별 메모 화면 안에서 실험/쟁점을 선택하고, `전체 / 사실·결과 / 기준 / 의견 / 결정 / 조치 / 질문`으로 좁혀 본다. 카드에는 내용 요약·대상·상태·주체를 표시하고 클릭하면 원문과 이력을 확인한다.

같은 결과 검토·미팅 브리프가 참조하는 항목을 보여주고, 원문 버전·실험 유효성이 바뀌면 관련 브리프를 ‘재검토 필요’로 표시한다. 과거 산출물은 당시 스냅샷을 보존한다.

## 7. 구현 순서와 기존 메모 처리

1. **주장 스냅샷 보존:** source_packet이 원래 claim 배열·종류·task_ids·claim별 인용·검토 정보를 유지하도록 한다. 원문과 사용자 수정 본문은 구분한다.
2. **작은 항목 추가:** 독립적인 knowledge unit과 대상/관계 저장을 추가한다. 전체 프로젝트 JSON 한 행만 계속 확장하기보다 실험·항목·연결을 작은 테이블로 분리하는 편이 후속 조회에 유리하다. 정확한 테이블 계약은 초안 검토 후 정한다.
3. **항목별 표시·저장:** 기존 claim 저장 버튼을 확장하고 전체 저장과 선택 항목 저장의 목적을 구분한다.
4. **기존 메모의 비파괴 변환:** 원 보고서 해시를 확인해 claims를 읽고 변환 후보를 만든다. SB17처럼 한 claim 안에 여러 시험이 있으면 추가 분할이 필요하다. 분할한 자식 항목마다 실제 지지 구간을 배정하고 부모의 모든 인용을 그대로 복사하지 않는다.
5. **검토 후 채택:** 시험 ID·의미 유형·상태가 불명확하면 미분류·미검토로 남긴다. 원 보고서가 없거나 해시가 다르면 본문만으로 확정 사실을 복원하지 않는다. 보관 메모와 수정 이력은 유지한다.
6. **업무 조립:** 고정된 합성 사례로 세 업무를 조립하고 기준일·무효화·의견/사실 구분·원문 추적을 확인한다.

원문 위치를 나중에도 열 수 있도록 job·E번호에만 의존하지 않는 locator가 필요하다. 기존 source의 보고서 해시와 별도 보관 원문 레지스트리의 문서 해시 검사를 계속 활용한다. 실제 내부 문서 권한과 기준일 처리도 항목 조회·원문 열기·브리프 생성에 동일하게 적용한다.

## 8. 이번 초안에서 검토할 것

[실제 공개자료 기반 시나리오 초안](../demo/internal_pipeline_v1/01_SCENARIO_DRAFT.md)과 [재구성한 내부 업무 문서](../demo/internal_pipeline_v1/02_SOURCE_DOCUMENTS.md)를 먼저 읽고, [작은 정보 단위와 세 업무 예시](../demo/internal_pipeline_v1/03_STRUCTURED_MEMO_AND_TASKS.md)에서 같은 자료가 어떻게 쓰이는지 확인한다. 현재 v1은 SB17/Pyzchiva의 공개 실험 요약·기관 평가를 참고하며, 실제 비공개 내부 문서를 입수한 것으로 표현하지 않는다.

우선 확인할 것은 자료 양이나 문서 형식보다, **결과·기준·의견·결정이 섞이지 않고 원문까지 추적되는가, 같은 항목을 세 업무에서 조건에 맞게 재사용할 수 있는가**다. 이번 초안은 데이터·구조 검토용이며 서비스에 적재되지 않았다.
