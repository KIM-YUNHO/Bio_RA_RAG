# 최근 업데이트 이후 한계점과 보완 순서

후속 구현: [근거 검사·검토 메모·제한된 추가 검색·운영 저장 업데이트](../rag/RA_WORKFLOW_UPDATE_2026-10-12.md). 아래 본문은 변경 전 4.6.7을 점검한 기준이며 당시 기록으로 보존한다.

검토 기준: 2026-10-12 KST. 최신 구현·실행 기록, 활성 제품 색인, 8775 서비스의 읽기 전용 `/api/summary`를 대조했다. 저장된 Luna 답변의 인용 14개는 문자 위치와 다시 대조했고, 원질문과 계획 단계의 재표현에 완료 검사를 적용했다. 신규 LLM 호출·검색 실행·테스트 전체 재실행은 없다. Git 이력이 없는 작업 폴더이므로 커밋 간 변경량을 확정하는 검토는 아니다. [이번 점검 기록](PROJECT_LIMITATIONS_AUDIT_2026-10-12.json).

### 이번 점검에서 구체적으로 재현한 완료 판정의 두 가지 불일치

동일한 저장 서비스 응답의 질문 두 표현을 현재 `fully_checkable_request`에 적용했다.

| 입력 | 완료 판정 가능 여부 |
|---|---|
| 원질문: “EMA에서 SB17 건강인 PK 시험의 실제 투여 용량과 경로를 알려줘.” | `true` |
| 계획의 요청: “EMA 문서에서 SB17 건강인 대상 PK 시험의 실제 투여 용량과 투여 경로를 확인해줘.” | `false` |

계획의 요청에서도 용량·경로·건강인·PK 항목은 모두 인식된다. ① 표현을 제거하고 남은 문자열을 확인하는 경로가 계획의 재표현을 처리하지 못해, 계획 요청의 `completion_checkable=false`와 `minimum_requirements_met=true`가 함께 나타난다.

② 현재 코드는 원질문도 별도로 검사한다. 원질문의 용량·경로·건강인·PK·동일 시험 검사는 통과하지만, `unambiguous_regimen`은 실패한다. 최종 답변에 과거 제안 90 mg과 실제 45 mg이 함께 있어 검사 함수가 서로 다른 두 용량을 센다. **계획과 실제를 구분한 설명을 용량 충돌로 처리하는 것이 이번 최종 `partial`의 직접적인 완료 검사 병목이다.** 저장된 최종 주장으로 원질문 검사를 다시 실행해 같은 실패를 재현했다. [검사 구현](../../rag/ra_requirements.py), [최종 상태 계산](../../rag/ra_answer.py), [저장 응답](../../data/runs/ra_luna_deployment_2026-10-12_v1/live_report.json), [재현 기록](PROJECT_LIMITATIONS_AUDIT_2026-10-12.json).

원질문 검사를 새로 추가하는 것만으로 해결되지 않는다. 실제/계획 수치의 역할을 보존하고 계획·원질문 검사의 판정 근거를 일관되게 표시해야 한다. 실제로 상충하는 투여 조건은 계속 차단하고, 근거 부족·완료 판정 미지원·수치 역할의 혼동은 구분한다. 이 보완을 임의 RA 질문의 의미 정확성 확보로 확대 해석하지 않는다.

## 다음 작업의 우선순위와 완료 기준

### 1. 저장 실패로 근거 선택·조건 보존·완료 판정을 보완

가장 먼저 다룰 것은 RA10의 조건·문서 식별, RA04의 제품별 설계·비교, CT-P43의 층화·분석 대상, 정상 SB17의 계획/실제 수치 구분과 재표현 완료 판정이다. 각각 ‘원문 미수록 / 검색 누락 / 공급 누락 / 선택 누락 / 의미 오류 / 과도한 차단 / 표시 오류’ 중 실제 병목을 기록한다.

완료 기준은 필요한 사실이 자체 최종 인용으로 지지되고, 조건·문서 이름·날짜가 남으며, 정상 사실의 손실이 줄어드는 것이다. 복합 질문의 남은 항목은 명시한다. 저장 응답 후처리 점검과 새 계획·검색·생성 실행은 별도 결과로 보고한다.

### 2. 고정 평가로 답변 신뢰성을 확인

개발 사례를 개선하는 동안 별도 문항·판정 기준을 준비하고, 변경을 고정한 뒤 실제 전체 경로를 평가한다. 제품 비교·기관/신청자 귀속·지침 적용·문서 시점·잘못된 전제·근거 부족을 포함한다. 정답과 평가 주석은 운영 검색·생성 입력에서 분리한다.

완료 기준은 완전 정답·조건 오류·누락·과도한 보류·비용을 함께 확인하고 기존 정상 답변 손실이 없는 것이다. 문항 수·허용 오류·호출 상한은 실행 전에 정한다. 현재 소규모 기록에서 임의의 전반적 정답률 목표를 소급해 만들지 않는다.

### 3. 쟁점별 RA 검토 메모를 만들고 부족 근거에만 추가 탐색

첫 산출물은 `쟁점 → 확인된 사실과 인용 → 적용 조건·비교 한계 → 상충 근거 → 미해결 항목 → 미팅 질문 초안`이다. 먼저 한 번 검색한 자료로 이 산출물을 만들어 실제 검토에 필요한 누락을 확인한다. 이후 부족한 항목만 추가 탐색하며 제품·기관·버전 경계, 횟수·토큰·비용 상한, 중복 근거 및 종료 조건을 기록한다.

완료 기준은 메모의 각 핵심 판단을 원문으로 추적하고, 미팅 질문이 구체적인 미해결 쟁점에 연결되는 것이다. 탐색 횟수나 메모 길이는 성과 지표로 쓰지 않는다. [기존 최종 목표](../rag/RA_GOAL_AND_UPDATE_PLAN_2026-10-12.md).

### 4. 업무 사용성과 운영을 보완

검토자가 원문과 메모를 함께 확인·수정하고 그 이력과 출처를 저장·내보낼 수 있게 한다. 버전·모델·색인·문서 상태·실행 비용을 결과와 연결하고 재시작 후 복원을 확인한다. 검색 준비 비용을 측정한 다음 BM25·후보 ID·동일 입력 계산 재사용을 검토한다.

최신 저장 Luna 요청은 총 32.875초 중 검색 17.094초, 생성·검토 12.297초였다. 검색 단계에도 최적화 여지가 있다는 단일 진단 자료다. 평균·p95나 반복 사용 성능으로 해석하지 않는다. [저장 시간 기록](../../data/runs/ra_luna_deployment_2026-10-12_v1/live_report.json).
