# RA 질문 처리 변경 기록

RA 파이프라인에서 사용자 질문을 읽고(계획), 검색하고, LLM 입력을 만드는 방식의 변경을 시간순으로 적는다. 새 내용은 아래에 날짜·시각 제목으로 추가한다. 이전 항목은 고치지 않고, 바뀐 판단은 새 항목에서 밝힌다.

관련 문서: [rag/RA_PROMPT_MODULES_2026-10-15.md](rag/RA_PROMPT_MODULES_2026-10-15.md) (생성 프롬프트 모듈)

## 용어

| 용어 | 뜻 |
|---|---|
| 하이브리드 순위 | dense 임베딩(bge-m3) 검색과 BM25 검색 순위를 RRF로 합치고, 계획기가 고른 문서 역할 가산점을 붙인 순위. 리랭커 없이 쓰던 기본 순위 |
| 리랭커 | 로컬 cross-encoder(`BAAI/bge-reranker-v2-m3`). 질의와 후보 문단을 한 쌍씩 읽어 점수를 매긴다. API 비용 없음, 로컬 계산 시간만 든다 |
| rerank-only | 리랭커 점수 순서만으로 후보를 정렬 |
| RRF (Reciprocal Rank Fusion) | 두 순위를 결합하는 방식. 후보마다 1/(60 + 하이브리드 순위) + 1/(60 + 리랭커 순위)로 정렬한다. 리랭커가 문단을 끌어올릴 수는 있지만 하이브리드가 강하게 잡은 문단을 혼자 묻지 못한다 |
| 요청문 (`request`) | 계획기가 쓴 작업 요청 문장 전체를 리랭커 질의로 사용 |
| ask (`ask`) | 계획기가 요청 사실마다 쓴 짧은 한 줄을 리랭커 질의로 사용(사실이 여럿이면 질의도 여럿, 문단은 가장 높은 점수) |
| `ask_unit` / `request_unit` | 위 질의 앞에 그 검색 그룹의 제품명(ID·브랜드)과 기관을 붙인 것(예: "SB17 Pyzchiva EMA: EU 최초 허가일") |
| 그룹 | 작업 × 제품 × 기관. 검색 후보는 그룹마다 따로 뽑는다 |
| atomic need | 제품 × 기관 × 사실 하나. 계획기 facet(`fact` 포함)·ask·query로 정의한다 |
| 후보 풀 | 리랭커가 다시 정렬하는 그룹별 하이브리드 상위 후보(기본 40개). 이 중 상위 8개가 LLM 입력으로 간다 |

## 2026-10-16 01:55 KST — 계획기가 질문을 읽고, 체크리스트로 생성, 문서 목록·correspondence 기본 검색

main 반영: `8568f8c`(planner-facets), `f4dc6da`(checklist-ask). 서비스(8885) 재시작 완료.

### 원칙

- 질문의 **의미 판단**(무엇을 묻는지, 어느 기관인지, 어떤 문서가 필요한지)은 계획 LLM이 한다.
- 코드는 **고유명사와 원문 사실만 확인**한다. 제품명이 레지스트리에 있는지, 계획기가 옮겨 적은 단어(기관명, 군·구간, endpoint, Part 번호)가 질문에 실제로 있는지, 답변 숫자·날짜가 인용한 원문에 있는지를 본다.
- 계획기의 해석은 **답변의 틀이 아니라 체크리스트**로 쓴다. 틀로 고정하면 정규식이든 LLM이든 같은 실패(칸 부족, 누락 시 답할 자리 없음)가 생긴다.

### 1. 체크리스트란

계획기가 읽은 "질문이 요구하는 것" 목록을, 생성 LLM에게 "빠뜨리지 말 것"으로 건네는 메모다.

계획기는 작업마다 다음을 출력한다.
- `answer_facets`: 요청한 사실의 종류(닫힌 선택지: dose_route, dosing_schedule, table_statistics, design, eligibility, reference_selection, analytical_bridge, document_status_scope, calculation 등)
- `items`: 따로 답해야 할 군·구간·시점(질문 원문 그대로; 예: "US ustekinumab군", "체중 55 kg 이하")
- `ask`: 그 facet이 이 질문에서 답해야 할 내용을 질문의 용어로 다시 쓴 한 줄(예: "피하 유지 투여의 시작 시점과 반복 간격")

코드는 항목이 질문에 실제로 있는지만 확인하고, 생성 LLM 입력에 이렇게 넣는다.

```
answer_checklist:
- CTP43 | 체중 구간별 정맥 유도 용량과 바이알 수 | 체중 55 kg 이하
- CTP43 | 체중 구간별 정맥 유도 용량과 바이알 수 | 55 kg 초과 85 kg 이하
- CTP43 | 체중 구간별 정맥 유도 용량과 바이알 수 | 85 kg 초과
- CTP43 | 피하 유지 투여 일정
```

생성 LLM은 각 줄을 claim(근거 인용이 달린 답변 문장)으로 답하거나 gap으로 적는다. claim 수는 기존 상한 안에서 자유이고, 목록에 없는 내용도 원 질문을 보고 답한다. 답변 뒤 완료 판정도 같은 facet을 쓴다(상태 표시만 바꾸고 claim을 지우지 않는다).

이전 "요구 항목 칸" 방식(줄마다 claim 1개)은 `RA_REQUIREMENT_MODE=slots`로만 남겼다.

### 3. 검색 이후 단계에 미칠 영향과 LLM 입력 단계 처리

현재 흐름(`rag/ra_retrieval.py`의 `retrieve`, `context`):
- 검색은 작업 × 제품 × 기관 조합(그룹)마다 상위 후보를 뽑는다. 계획기가 고른 문서 역할은 순위 가산점이다.
- 패킹은 모든 그룹의 1위, 그다음 2위… 순으로 입력 예산이 찰 때까지 돌아가며 채운다.
- 재순위는 꺼져 있다. 재순위 모델은 로컬 cross-encoder(`BAAI/bge-reranker-v2-m3`, `rag/rerank.py`)라 API 비용은 없고 로컬 계산 시간만 든다.
- 체크리스트는 생성 지시에만 쓰이고, 어떤 근거를 넣을지는 고르지 않는다.

오늘 변경의 영향:
1. correspondence가 들어와 그룹마다 후보가 늘었다. 보충신청 허가서한이 여러 개인 제품은 원 허가서한과 순위를 다툰다.
2. 역할 가산점이 계획기 선택에 달려 있어, 역할 선택이 흔들리면 그룹 안 순위도 흔들린다(Q5 2회차).
3. 역할이 3개로 늘면 가산점이 분산된다(Q1 캐나다 결정 요약서가 밀린 원인으로 추정).
4. 재순위를 켜도 지금은 계획기 검색어 기준이라 체크리스트와 맞물리지 않는다.

LLM 입력 단계에서 할 수 있는 방법:

| 방법 | 내용 |
|---|---|
| A. 체크리스트 기준 패킹 | 체크리스트 항목 × 제품 × 기관마다 가장 맞는 근거 1개를 먼저 확보하고, 남은 예산을 지금처럼 돌아가며 채움 |
| B. 재순위 질의 = ask | 로컬 재순위 모델로 그룹마다 계획기의 ask 기준으로 후보를 재정렬(후보 수를 제한해 지연 관리) |
| C. 근거를 단위별로 정리해 제시 | 근거를 제품 × 기관 단위로 묶고 문서 종류·날짜를 머리에 표시 |
| D. 중복 문서 접기 | 같은 내용의 허가서한·라벨 판본을 하나로(옵션은 있으나 꺼짐) |

진행: A 효과부터 측정한다(저장된 계획으로 검색·패킹만 다시 해서, LLM 입력 근거에 정답 값이 들어가는지 비교; API 비용 없음).

## 2026-10-16 04:22 KST — 설계: atomic need(제품 × 기관 × 사실 하나)로 검색·리랭커·패킹·생성·평가를 통일

### 왜 (지금까지 측정에서 반복된 구조)

- 리랭커는 "사실 하나를 찾는" 질의에서 강하다(사실 정답 @8 0.78 → 0.91). 약했던 경우는 모두 질의가 여러 사실을 한꺼번에 담을 때다(열거형, 날짜 여러 개를 묻는 타임라인, 용량·바이알·일정을 함께 묻는 세부 질문).
- 근거가 많아지면 생성 LLM이 제품을 섞는다(end-to-end에서 claim 제품 불일치 탈락 증가).
- 근본 원인: "무엇을 찾아야 하는지(정보 요구)"가 단계마다 다른 형태로 흩어져 있다. 검색은 계획기의 영어 검색어(질문 전체를 뭉뚱그림), 리랭커는 요청문 또는 ask, 패킹은 그룹 순서, 생성은 체크리스트, 평가는 정답 묶음(제품 × 기관 × 사실).

### 무엇을

정보 요구를 **atomic 단위(제품 × 기관 × 사실 하나)**로 한 번 정의하고 모든 단계가 공유한다.

| 단계 | atomic need 방식 |
|---|---|
| 계획기 | 작업마다 요청 사실 목록을 낸다. 사실마다 facet(닫힌 종류; 목록에 없으면 `fact`), ask(질문 용어의 한국어 한 줄), query(문서에서 찾을 짧은 영어 검색어), 항목(따로 답할 군·구간·시점). 코드는 이것을 작업의 제품 × 기관과 곱해 atomic need 목록을 만든다 |
| 검색 | atomic need마다 그 제품·기관 문서 안에서 상위 k개(2~4개). 열거형 질문은 단일 사실 검색 여러 개가 된다 |
| 리랭커 | atomic need 문장(제품·기관 + ask)을 질의로 쓴다. 하이브리드 순위를 갈아치우지 않고 RRF로 결합한다(날짜·숫자처럼 BM25가 정확히 잡은 페이지를 보호) |
| 패킹 | atomic need별 근거 유무가 곧 커버리지. 예산은 요구 수 × k로 미리 정해진다 |
| 생성 | 근거를 atomic need별로 묶어 보여준다(체크리스트와 같은 단위) |
| 평가 | 골든셋 정답 묶음과 1:1 대응. 어느 단계에서 빠졌는지 바로 보인다 |

- facet이 없는 열린 작업(심사 판단, 지침 해석)은 atomic need가 "제품 × 기관 × 작업 요청문"이 되어 지금과 같다.
- 안전망: 계획기가 사실을 빠뜨릴 수 있으므로 작업 요청문 기준 검색을 함께 남긴다(체크리스트가 "목록 밖도 답한다"인 것과 같은 원리).

### 비용·위험

- atomic need 수: Q1은 5개 제품 × 3개 기관 × 2개 날짜 = 30개. 검색은 로컬이라 빠르고, 리랭커는 30 × 후보 40 = 1,200쌍(GPU 몇 초 추정), LLM 입력은 30 × 3 = 90블록(지금 Q1 130블록보다 작음).

4. 판정: 전체 점수뿐 아니라 묶음별 표(사실 정답·QA_candidates·세부 질문·감시·열거형·타임라인)가 모두 "그룹 방식 + 리랭커 없음"보다 나빠지지 않을 것. 하나라도 크게 떨어지면 반영하지 않는다.
