- 3열 CSS grid. ③은 기본 닫힘(2열), 열면 3열. 열 사이 경계는 끌어서 폭 조절, ①도 접을 수 있게 한다.

### 2.1 ① 왼쪽: 적재 현황과 범위 선택

- **트리**: 성분 → 바이오시밀러 제품 → 문서. 성분 체크 = 그 성분의 바이오시밀러 전체. 기관은 별도 체크(EMA/FDA/HC), 공통 지침도 별도 체크.
- **대조약 자료**는 바이오시밀러와 다른 묶음으로 보인다. 체크하면 대조약 스냅샷(4장)이 그 턴의 검색 범위에 들어간다. 스냅샷을 만들기 전(6단계 전)에는 "수집됨, 검색 색인 준비 전"으로 비활성.
- **문서 체크박스**(2026-10-13 확정): 제품을 펼치면 문서별 체크. 고르면 `documents` 범위로 보낸다(서버는 이미 지원). 문서를 하나라도 고르면 제품·기관 체크보다 문서 선택이 우선임을 선택 요약에 표시한다.
- **제품×기관 격자**: 칸마다 `검색 가능 문서/수집 문서` 수, 빈칸은 사유(캐나다 미허가, FDA 심사 패키지 미공개). 칸을 누르면 그 조합만 선택된다. 체크박스만으로는 "SB17의 HC 문서가 실제로 있는지"가 안 보이기 때문이다.
- **선택 요약**: "SB17·CTP43 × EMA·FDA · 지침 포함 · 문서 34개". 아무것도 고르지 않으면 지금처럼 검색 허용 자료 전체(대조약 제외).
- **새 API `GET /api/inventory`**: `targets.json`(성분·제품·kind·licences) + `data/catalog/documents.jsonl`(수집 문서 수) + 파이프라인 문서 목록(색인 문서·청크 수) + 지침·대조약 스냅샷. 성분·제품이 늘어도 `targets.json` 구조로 자동 표시된다.
- 선택은 **턴마다** 적용한다. 각 답변 머리에 그 턴에 쓴 범위를 칩으로 남긴다(대화 중간에 범위를 바꿔도 어느 답이 어느 범위였는지 보인다).

### 2.2 ② 가운데: 채팅

- 말풍선: 사용자 질문 / 답변 카드. 답변 카드 안에 상태 배지(근거 지지 검토·부분 답변·근거 미확보), 답변 본문, 인용 번호(`[E3]` 누르면 ③이 열림), 표·그림 카드, 접힘 영역(항목별 확인 상태, 검토 메모·미팅 질문, 질문 해석·검색 범위).
- 근거가 대조약 스냅샷에서 왔으면 인용에 "대조약 문서" 표시를 붙인다. 바이오시밀러 심사보고서 안의 EU-Stelara 비교 자료와 Stelara 자체 라벨을 화면에서 구분하기 위해서다.
- 진행 상태는 답변 자리에 단계로 표시(질문 해석 → 근거 검색 → 답변·근거 검토). 서버가 1건씩 처리하므로 처리 중엔 입력을 잠근다.
- 입력창의 `/`는 스킬 메뉴를 연다(7장).
- 기존 기능은 전부 유지: 검토 의견·이력, 미팅 질문 편집, JSON/Markdown 저장. "이전 질문 다시 열기"는 "대화 목록"이 된다(기존 단일 질문은 1턴 대화로 보인다).

### 2.3 채팅 안의 표·그림

- **언제 띄우나**: 답변이 인용한 근거 중 `structure.kind`가 `table_candidate`·`figure_candidate`이면 답변 아래에 카드로 자동 표시. 질문이 표·그림을 찾았는데 인용되지 않았으면 검색된 표·그림 후보를 "관련 표·그림" 접힘으로 보여준다.
- **표**: 근거 `text`의 `<table>` HTML을 허용 태그(table, thead, tbody, tr, th, td와 rowspan·colspan)만 남겨 DOM으로 다시 만든다(문자열을 그대로 `innerHTML`에 넣지 않는다). 캡션·각주를 함께 보이고, 인용 문장과 같은 칸은 강조한다.
- **원문 이미지 토글**: 추출 표 옆에 해당 영역을 잘라낸 원문 이미지를 둔다. 표·그림의 의미 검토가 끝나지 않았으므로(10/10 릴리스 명세 기준 검토 필요 표현 535개, 그림 설명 709개) 추출 표를 원문과 바로 대조할 수 있어야 한다.
- **그림**: 영역 잘라낸 이미지 + 캡션. 로컬 VLM 설명은 "미검토 설명"으로 표시.
- **수식 조각**(`$ AUC_{inf} $` 같은 것): 외부 KaTeX는 CSP 때문에 못 쓴다. 아래첨자·위첨자만 단순 변환하는 규칙을 두고, 변환 못 하면 원문 그대로 둔다.
- **새 API `GET /api/jobs/<id>/evidence/<eid>/crop`**: 서버가 저장된 보고서의 `source_refs`에서 문서와 영역을 찾는다. 클라이언트는 파일 경로를 보내지 않는다.

### 2.4 ③ 오른쪽: 근거 원문 페이지 (간단 보기)

③은 **답변을 읽다가 근거를 바로 확인하는 간단 보기**다. 전처리 결과·영역 구조·청크까지 보는 상세 검토는 지금처럼 8766 검토 페이지에서 한다(2026-10-13 확정: 8766은 별도 유지).

- **기본 닫힘.** 채팅의 "원문 보기" 버튼이나 인용 번호를 누르면 열린다. 닫기 버튼과 폭 조절.
- **표시**: 페이지 이미지 + 근거 영역 강조(`bbox_pdf`를 이미지 좌표로 변환). 영역 좌표가 없는 근거(지침·대조약)는 인용 문장을 PDF 텍스트에서 찾아 강조하고(PyMuPDF `search_for`), 둘 다 실패하면 "강조 위치 없음"이라고 적는다.
- **머리 정보**: 기관·제품·문서 제목·PDF 페이지와 인쇄 쪽 번호(`pdf_page_label`), 지침이면 상태(Draft/Final/철회)와 확인 시점.
- **조작은 최소한**: 이전/다음 페이지, 이 답변의 다른 근거 목록(탭), "8766에서 상세 보기"(같은 문서·페이지·영역으로 열림), "원본 PDF 열기".
- **구현**: 8775에 페이지 렌더링 경로를 추가한다(`review_viewer/data.py`의 렌더링 로직을 공용 모듈로 빼서 함께 쓴다). 렌더 대상은 활성 릴리스와 지침·대조약 스냅샷에 있는 `(document_id, version_id)`만 허용하고 원본 sha256을 확인한다. HC 웹 문서는 `rendered_path` PDF를 쓴다. 렌더 결과는 LRU 캐시.

## 3. 멀티턴 (2026-10-13 B 방식 확정)

### 3.1 멀티턴에 필요한 세 가지

1. **대화 기록 저장**: 어떤 질문들이 한 대화로 이어졌는지.
2. **후속 질문 해석**: "그럼 FDA는?", "그 시험의 ADA는?"처럼 생략된 제품·시험·기관·주제를 앞 턴에서 채운다. 멀티턴의 핵심은 이것이다.
3. **앞 결과 다시 쓰기**: "그 표 다시 보여줘", "2번 근거 원문"처럼 새 검색이 필요 없는 요청.

### 3.2 방식 비교 (기록)

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 대화 전체 전달 | 앞의 질문·답변을 모두 생성 모델 입력에 넣는다 | 구현이 간단하고 자연스럽다 | 인용 검사·검토 기록·평가가 "질문 1개" 기준이라 깨진다. 앞 답의 오류가 다음 답으로 옮겨간다. 토큰이 턴마다 늘고 재현이 어렵다 |
| **B. 독립 질문으로 바꾼 뒤 기존 파이프라인 (채택)** | 후속 질문을 "EMA 문서에서 SB17-1001 시험의 …"처럼 혼자 읽히는 질문으로 바꿔 지금 경로에 넣는다 | 턴마다 답변이 단독으로 원문 검증된다. 기존 검사·검토 기록·평가를 그대로 쓴다. 바뀐 질문을 사용자에게 보여주고 고치게 할 수 있다 | 바꾸기가 틀릴 수 있다 → 화면에서 확인·수정 |
| C. B + 앞 턴 근거 우선 검색 | B에 더해 앞 턴이 인용한 문서·시험을 먼저 찾는다 | 후속 질문 정확도가 오를 수 있다 | 범위가 앞 턴에 갇힐 위험. B를 측정한 뒤 필요할 때만 |

### 3.3 B의 동작

- **대화 상태는 원문 대화가 아니라 구조화된 칸**으로 둔다: 직전 독립 질문, 제품, 시험, 기관, 주제, 문서군, 대조약 포함 여부, 인용한 근거 ID. 값은 앞 턴 보고서의 `understanding`(products, studies, jurisdictions, topic, doc_groups)에서 가져온다.
- **1단계, 규칙** (모델 호출 없음):
  - 새 질문에 제품·시험·기관 언급이 없으면 앞 턴 값을 이어받는다.
  - 기관만 언급("FDA는?")하면 기관만 바꾼다. 제품만 언급하면 제품만 바꾼다.
  - "다른 제품도", "전체 제품" 같은 명시 표현은 이어받기를 푼다.
  - 제품·시험·주제가 모두 바뀌면 새 주제로 보고 이어받지 않는다.
  - 어느 규칙이 작동했는지와 이어받은 값을 턴 기록에 남긴다.
- **2단계, 모델**: 지시어("그 결과", "그 차이", "아까 그 표")처럼 규칙으로 문장이 완성되지 않으면 기존 해석 호출(`rag/ra_tasks.py`의 `interpret`)에 대화 상태를 함께 넣고 `standalone_question` 칸을 같이 받는다. **해석 호출을 하나 더 만들지 않으므로 요청당 최대 3회가 유지된다.**
- **화면 확인**: 질문 아래에 "이렇게 이해했습니다: EMA 문서에서 SB17-1001 시험의 …" + [수정]. 고치면 그 문장으로 다시 실행한다.
- **범위 우선순위**: ① 왼쪽 선택이 바깥 경계(넘으면 지금의 범위 충돌 경고) → 그 안에서 질문의 명시 언급 → 이어받은 값.
- **앞 결과 다시 쓰기는 문장 해석 대신 버튼**으로 한다(표 보기, 원문 보기, 메모 저장, 이 질문을 비교표 스킬로 실행). 오해석이 없고 모델 호출도 없다.
- "새 대화" 버튼으로 상태를 비운다.

### 3.4 저장

- `data/runs/ra_conversations/<conversation_id>.json`: `turns[{turn, kind(question|skill), user_text, standalone_question, inherited, rule, scope, job_id | skill_run_id}]`.
- 보고서(`data/runs/ra_service_reports/`)와 검토 기록(보고서 sha256에 묶임)은 지금 형식 그대로. 대화 파일은 job ID로 보고서를 가리키기만 한다.
- `#conv=<id>`로 복원. 질문 제출 요청에 `conversation_id`를 추가하고 서버가 검사한다.

### 3.5 검증

- **후속 질문 세트**: 2~3턴 대화 약 30개(제품 전환, 기관 전환, 시험 전환, 지시어, 새 주제, 범위 충돌). 턴마다 기대하는 이어받기 결과(제품·시험·기관)를 정답으로 둔다. 실무 질문이 없으므로 기존 고정 문항에서 템플릿으로 만든다.
- 규칙 단계는 모델 호출 없이 채점하고 회귀 테스트로 고정한다. 모델 단계는 고정한 소수 문항(예: 8개)만 API로 실행하고 호출 수를 기록한다.
- 기존 회귀(최근 1,090개)를 유지한다.

## 4. 대조약 별도 색인 (2026-10-13 사용자 제안 검토)

**판단: 별도 스냅샷으로 두고 필요할 때만 검색하는 방식이 맞다.** 공통 지침이 이미 같은 구조(별도 스냅샷 + 문서 역할로 검색 여부 결정)로 운영되고 있어 새 구조를 만들 필요도 없다.

### 4.1 섞지 않고 분리하는 이유

| 이유 | 확인한 사실 |
|---|---|
| 크기가 바이오시밀러 전체보다 크다 | Stelara 88문서·4,380쪽(텍스트 층 있는 쪽 약 3,260). 활성 릴리스는 5제품 92문서·4,160쪽. 섞으면 Stelara 자체 임상(건선·크론병 등 본 임상)이 바이오시밀러 비교 시험과 검색 순위를 다툰다 |
| 이름이 겹친다 | 바이오시밀러 심사보고서에 "EU-Stelara", "US-Stelara"가 비교약으로 계속 나온다. 한 색인에 두면 "Stelara 자료"가 비교약 데이터인지 Stelara 자체 문서인지 구분이 흐려진다 |
| 활성 릴리스를 건드리지 않는다 | `rag_finalization_2026-10-10_v2`(10,088벡터)를 다른 세션·평가가 버전 기준으로 쓴다. 분리하면 재색인·재평가가 필요 없다 |
| 갱신 주기가 다르다 | Stelara 라벨은 자주 개정된다(최신 FDA 라벨 SUPPL-173, 2026-09-01). 스냅샷만 따로 다시 만들 수 있다 |

### 4.2 구조

- **대조약 스냅샷**: `GuidelineIndex`와 같은 틀(`rag/ra_sources.py`). 페이지 단위 native 청크, `product_id = CNTO1275`, `product_kind = reference`, 원본·파싱 sha256을 manifest에 기록하고 시작할 때 검사.
- **검색**: 처음엔 지침처럼 BM25만. 측정해서 부족하면 bge-m3를 더한다.
- **들어가는 문서**: 텍스트 층이 있는 쪽 전부. 기본 검색 여부는 제품 자료와 같은 `document_kinds.json` 규칙(`default_search`)을 따른다.
  - 현행 라벨 3개는 전 쪽 텍스트 있음: EU 제품정보 190쪽, US 최신 라벨 57쪽, HC 제품 모노그래프 91쪽. EPAR 58쪽, EMA 변경 보고서 11개(적응증 확대 이력)도 텍스트 있음.
  - 검색 안 되는 부분: EMA RMP 109쪽 전부와 2009년 FDA 심사 스캔본 일부(텍스트 없는 쪽 약 1,120쪽). OCR하지 않는다는 결정(2026-10-08)을 유지하고, 화면과 답변에 "텍스트 없는 쪽은 검색되지 않음"을 표시한다.

### 4.3 언제 검색하나

다음 중 하나일 때만 대조약 스냅샷을 검색한다. 최종 결정은 코드가 한다.

1. **사용자가 ①에서 "대조약 자료"를 체크**했을 때.
2. **질문이 Stelara 자체 문서를 묻는다고 계획되고 코드 검사를 통과**했을 때. 질문 계획의 문서 역할에 `reference_product`를 추가한다. 지침 역할과 같은 방식으로, 질문에 대조약 자체 문서를 가리키는 표현(라벨, 허가사항, 적응증, 승인 이력, 대조약 문서 등)이 있을 때만 남기고 아니면 지운다.
   - 예: "SB17과 EU-Stelara의 PK 비교"는 바이오시밀러 심사보고서에 답이 있으므로 대조약 스냅샷을 검색하지 않는다.
   - 예: "Stelara 라벨의 크론병 용법"은 검색한다.
3. **스킬이 대조약 자료를 쓸 때.** 예: 라벨 대조 스킬(7장).

답변에서는 바이오시밀러 문서 근거와 대조약 문서 근거를 나눠 보여준다. 두 색인을 같이 검색할 때는 문맥 예산을 나눠 배정해서 한쪽이 다른 쪽을 밀어내지 않게 한다.

### 4.4 검증

- 대조약 질문 소수(라벨 용법·적응증·승인 이력)와, 대조약을 검색하면 안 되는 질문(바이오시밀러 문서의 EU-Stelara 비교)을 함께 고정한다. 검색 여부 판정을 모델 호출 없이 채점한다.
- 기존 회귀에서 대조약을 체크하지 않은 질문의 검색 결과가 바뀌지 않는지 확인한다.

## 7. 활용 기능을 솔루션에 넣는 방식: 채팅 + 스킬

### 7.1 판단

**채팅을 중심에 두고 활용 기능을 스킬로 두는 방향이 맞다.** 다만 세 가지를 조건으로 한다.

1. **모든 기능을 스킬로 만들지 않는다.** 결과물을 만드는 고정 작업만 스킬이다.
2. **스킬은 처음엔 사용자가 명시적으로 실행한다.** 모델이 알아서 스킬을 골라 돌리는 방식은 스킬마다 정답셋이 생긴 뒤에 검토한다.
3. **스킬의 결과는 채팅 문장이 아니라 결과물(표·목록·연대표)이다.** 결과물의 칸마다 원문이 연결된다.

### 7.2 세 종류로 나눈다

| 종류 | 무엇 | 해당 기능 | 화면에서의 위치 |
|---|---|---|---|
| **스킬** | 정해진 입력으로 정해진 형식의 결과물을 만드는 작업 | 선례 비교표(기관 차이 보기 포함), 지적사항 목록, 허가 타임라인, 지침 체크리스트, 라벨 대조, 자사 초안 점검, 변경 내역 조회 | 입력창 `/` 메뉴, 답변 뒤 제안 칩 |
| **기본 기능** | 모든 답변과 결과물에 항상 붙는 것 | 주장·칸 단위 검토, 내보내기, 원문 보기 | 답변 카드·결과물의 버튼 |
| **백그라운드 작업** | 채팅과 상관없이 주기적으로 도는 것 | 변경 감시 | ①에 "새 버전 3건" 같은 알림 배지. 내용은 "변경 내역" 스킬로 연다 |

### 7.3 스킬을 명시 실행으로 시작하는 이유

| 이유 | 설명 |
|---|---|
| 비용 | 비교표는 질문 × 제품 × 최대 3회 호출이다(예: 8항목 × 5제품이면 최대 120회). 실행 전에 예상 호출 수를 보여주고 확인을 받아야 한다. 모델이 대화 중에 알아서 돌리면 통제가 안 된다 |
| 재현성 | 같은 입력이면 같은 행·열 구조가 나와야 비교표를 문서에 쓸 수 있다. 질문 문장에 따라 형식이 달라지면 안 된다 |
| 검증 | 처리 결정은 코드로 고정하고 정답셋·회귀로 검증하는 것이 이 프로젝트의 원칙이다. 스킬 단위로 정답셋을 둘 수 있다 |
| 잘못된 실행 방지 | "SB17이랑 ABP654 비교해줘"가 질문 하나인지 비교표 스킬인지 모델이 잘못 고르면 비싼 작업이 엉뚱하게 돈다 |

자연어는 **제안까지만** 한다. 규칙으로 스킬과 맞는 질문을 알아보면(예: 제품 3개 이상 + "비교/표") 답변 아래에 "선례 비교표 스킬로 실행할까요? 예상 호출 최대 45회" 칩을 띄우고, 사용자가 누르면 실행한다.

### 7.4 스킬 공통 계약

모든 스킬은 같은 틀을 따른다. 새 스킬을 붙일 때 화면·저장·검토를 다시 만들지 않기 위해서다.

| 항목 | 내용 |
|---|---|
| 정의 | 이름, 설명, 매개변수 스키마(예: 비교 항목 목록), 쓰는 데이터 출처(검증 관측값 / RAG / 카탈로그 / 지침 / 대조약 스냅샷) |
| 입력 | ①의 현재 범위 + 스킬 매개변수 |
| 비용 | 실행 전 예상 호출 수·상한. 상한을 넘으면 실행하지 않는다 |
| 결과 형식 | 표 / 목록 / 연대표 중 하나 |
| 칸마다 붙는 것 | 근거(`document_id`, `version_id`, `pdf_page`, 영역) → ③으로 열림. 상태: `code_verified`(코드 검증 관측값) / `rag_candidate`(RAG 답, 미검토) / `not_found`(찾은 범위에서 없음, 문서 전체의 부재가 아님) / `human_reviewed` |
| 저장 | `data/runs/ra_skill_runs/<id>.json`. 대화 턴에 `skill_run_id`로 연결. 쓴 코드·데이터 버전 기록 |
| 다시 실행 | 데이터가 바뀌면 같은 매개변수로 다시 돌리고 이전 결과와 차이를 보여준다 |
| 검증 | 스킬마다 원문 판정 정답셋과 회귀 테스트 |

### 7.5 화면

- 스킬 결과는 채팅에 **요약 카드**로 들어간다: "선례 비교표 · 5제품 × 3기관 × 8항목 · 채움 92/120 · 미검토 40" + 미리보기.
- **"크게 보기"**를 누르면 ② 영역이 결과물 화면으로 넓어지고 채팅은 접힌다. ①(범위)과 ③(원문)은 그대로라 3분할 구조가 유지된다. 칸을 누르면 ③에 원문이 열린다.
- 결과물에 대한 후속 요청("FDA만", "ADA 항목 추가")은 처음엔 결과물 화면의 필터·항목 버튼으로 한다. 자연어로 결과물을 고치는 기능은 나중에 본다.

### 7.6 첫 스킬: 선례 비교표

- 칸을 채우는 순서: ① 검증된 관측값(`data/evidence/observations.jsonl`, 코드 검증) → ② 없으면 조사 묶음(항목별 고정 질문)으로 RA 파이프라인 실행 → `rag_candidate`로 표시 → ③ 그래도 없으면 `not_found`.
- "차이만 보기"는 같은 제품의 기관별 값이 다른 칸만 남긴다. 문서에 실제로 다르게 인쇄된 값(예: FDA 자체 재분석 GMR)과 추출 오류를 구분하기 위해 두 값 모두 원문 링크를 단다.
- 완료 기준: 원래 3제품 칸은 기존 정답(관측값 정답 74행)과 일치, 새 2제품은 Claude가 원문을 보고 판정한 칸 표본과 대조, 실행 전 예상 호출 수와 실제 호출 수가 기록됨.

- 대신 새 화면을 `web/`으로 옮기고 `static/`을 10-12 스냅샷(`data/runs/ra_today_completion_2026-10-12_v4_ces/code_snapshot/`)에서 복원했다. 4개 파일의 sha256이 스냅샷과 같고, 8775의 `/app.js` 응답 해시도 같다. 8775는 재시작 없이 이전 화면으로 돌아왔다.
- 새 화면을 운영에 쓰려면 8775 재시작이 필요하고, 그러면 파이프라인도 4.8.9가 된다. 이 결정은 사용자가 한다. 재시작한 뒤에는 `static/`을 지워도 된다(평가 스크립트 몇 개가 이 폴더의 해시를 기록하고 있으니 그때 함께 정리한다).
