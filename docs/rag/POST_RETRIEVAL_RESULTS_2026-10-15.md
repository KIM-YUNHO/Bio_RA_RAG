## 4. 조건 확인 (근거 부족 판단의 첫 부분)

### 4.1 문제
검토 단계(`rag/ra_review.py`)는 "원문의 실제 조건이 질문의 조건과 달라도 지지되는 사실"로 본다. 답이 조건(SC)을 빼고 쓰면 질문(IV)의 답처럼 읽힌다(3.4의 PK_023).

### 4.2 방법 (규칙, LLM 호출 없음)
- 질문에서 정해진 조건어를 읽는다: 투여 경로(정맥/피하), 기기(자가주사기·프리필드·바이알), 적응증(크론병·궤양성 대장염·건선성 관절염·판상 건선), 특수 대상군(소아·청소년·임부·고령자)
- 답이 인용한 원문 + 인용 블록의 절 제목·표 캡션에서 그 조건을 찾는다. 본문 전체는 보지 않는다(다른 조건 이야기가 섞여 진짜 혼동을 가릴 수 있음).
- 없으면 gap 추가, 답 앞에 안내문("질문한 조건(정맥(IV))을 명시한 근거를 확인하지 못했습니다. 인용한 근거는 피하(SC) 자료입니다…"), answered → partial. **주장·인용·값은 바꾸지 않는다.**

### 4.3 결과

- 문제: v1은 답 전체의 인용 범위에 질문 조건(IV)이 한 번이라도 나오면 통과시켰다. PK_023처럼 다른 주장이 "SC 자료를 IV로 외삽"을 인용하면, SC 시험의 GMR 값 주장도 함께 통과했다(4-2-1).
- 추가 규칙: **결과 값**(소수 또는 %; `45 mg/0.5 mL` 같은 용량·부피는 제외)을 말하는 주장이 그 조건 차원의 말(정맥/피하, 적응증 등)을 문장에 쓰지 않았고, **자기 인용 범위**에 질문 조건이 없으면 경고한다. 결과에 `value_claims`(주장 ID)를 남긴다. 주장이 "피하 투여에서 …"처럼 자기 조건을 밝히면 경고하지 않는다.

- 수정으로 살아난 PK_023 지어내기 5개를 넣어 보면 v2는 **5/5**를 잡는다(v1은 3/5).
- 주의: 이 규칙은 PK_023과 조건 질문 8개(확인용 4개 포함)를 모두 본 뒤 만들었다. 그래서 조건 질문의 확인용 4개는 더 이상 처음 보는 질문이 아니다.

## 4-1. 답하기 전 충분성 판단 (근거 부족 판단 2-2): 진단 결과 — 점수 기준은 쓸 수 없음

PoC의 신뢰성 검사처럼 "리랭커 점수가 기준보다 낮으면 근거 부족"으로 판단할 수 있는지, H 설정(리랭커 + 1위 보장, k=12)의 검색 결과로 확인했다(LLM 호출 없음, `eval/sufficiency_diagnosis.py`). 점수는 공급된 근거 중 최고 리랭커 점수(시그모이드, 0~1)이다.

| 묶음 | 문항 | 한국어 질문 점수 (최소 / 중앙) | 영어 검색어 점수 (최소 / 중앙) |
| :-- | --: | :-- | :-- |
| 답할 수 있고 정답 근거가 검색됨 | 97 | 0.499 / 0.959 | 0.647 / 0.991 |
| 답할 수 있는데 정답 근거가 안 들어옴 (재검색 필요) | 7 | 0.738 / 0.922 | 0.553 / 0.965 |
| **자료 없음** (absent 4, qa_gold 1, 조건 질문 6) | 11 | **0.869 / 0.990** | **0.913 / 0.994** |

- **자료 없는 질문의 점수가 오히려 더 높다** (AUC 0.28~0.41, 0.5보다 낮음). 자료 없는 질문도 주제가 같은 근거(IV를 물었는데 SC 시험, UC를 물었는데 건선 시험)가 검색되기 때문이다.
- 재검색이 필요한 질문도 점수가 높아서, 점수로는 재검색 시점을 정할 수 없다.
- 결론: **이 데이터에서는 점수 기준 판단을 만들지 않는다.** PoC에서 효과가 있었던 건 PoC가 여러 성분·기관 문서를 한꺼번에 검색해서 관련 없는 근거가 자주 섞였기 때문으로 보인다. 통합은 제품×기관 그룹으로 범위를 좁혀서 검색 결과의 주제가 거의 항상 맞는다.
- "자료 없음"은 점수가 아니라 **조건·대상의 불일치**로 나타나므로 4장의 조건 확인과 답변 뒤 검토가 맡는 게 맞다. 범위 밖 질문(N02)은 질문 해석 단계에서 이미 걸러진다.

## 4-3. 변형 질문 1단계: 화면에서 제품·기관을 고르지 않은 질문으로 재진단

변형 질문(검색어를 문서 표현으로 바꿔 더 검색)이 해결하는 것은 정답 근거가 **후보(상위 40개)에도 못 드는 경우**다. 지금까지 진단은 화면에서 제품·기관을 고른 조건이라 검색 범위가 좁았다. 실제 사용자처럼 **아무것도 고르지 않은** 조건으로 같은 101문항을 다시 진단했다(`--no-ui-selection`, 질문 해석 105회, $0.06).

| 조건 | 설정 | 공급 / 156 | 고르기 탈락 | **후보에도 못 듦** | 평균 프롬프트 토큰 |
| :-- | :-- | --: | --: | --: | --: |
| 화면 선택 있음 | 기준 (k=8) | 136 | 18 | 2 | 약 7.2k |
| 화면 선택 있음 | H (리랭커, k=12) | 150 | 5 | **1** | 약 10.6k |
| 화면 선택 없음 | 기준 (k=8) | 135 | 20 | 1 | 약 17.2k |
| 화면 선택 없음 | H (리랭커, k=12) | 144 | 11 | **1** | 약 25.7k |

- **후보에도 못 드는 근거는 두 조건 모두 1개뿐이다.** 질문 해석이 이미 과제마다 영어 검색어를 1~2개 만들고(가벼운 변형 질문), 제품×기관 그룹으로 나눠 검색하기 때문이다. → **변형 질문은 지금 만들지 않는다.**
- 남은 1개(`EMA_UST_IMMUNOGENICITY_005`, SB17 EPAR 49쪽)는 "NAb 검사법"과 "NAb 시료 선택 조건" 두 부분을 묻는 질문의 뒷부분이다. 검색어 표현보다 **질문의 한 부분이 빠진 문제**라서 다음 작업인 질문 분해(빠진 부분만 재검색)가 맡을 대상이다.
- 화면 선택이 없어도 리랭커는 효과가 있다(135 → 144). 다만 `EMA_UST_IMMUNOGENICITY_022`는 기준 순위 4위였던 쪽(정답 3단위)을 리랭커가 밀어냈다.
- 화면 선택이 없으면 프롬프트가 2배 이상 커진다. 특히 **제품명 없이 시험 번호만 있는 질문**(예: "20190230의 ADA sampling schedule", "BM12H-NHV-01-G-01에서 …")은 질문 해석이 제품을 정하지 못해 모든 제품·기관을 검색한다. 그룹이 20~60개가 되고 프롬프트가 약 61k 토큰으로 예산(65,536)에 거의 닿는다. 시험 번호 → 제품 연결은 질문 해석 단계(담당 밖)라 6장에 기록한다.
- 실행 중 리랭커 버그를 찾아 고쳤다: 후보가 0개인 그룹(예: 해당 기관 문서가 없는 그룹)에서 `reranker candidate limit must be 1..150` 오류로 멈췄다. 서비스에서도 같은 조건이면 멈추므로 `reranked_hits`가 빈 후보면 빈 결과를 돌려주게 했다.

## 4-4. 질문 분해 (A 범위: 1차 검색 뒤 빠진 부분만 재검색) 진단: 지금 평가 세트에서는 할 일이 거의 없음

저장된 결과만 다시 읽었다(LLM 호출 없음). 확인한 것은 세 가지다: 검색에서 빠진 근거가 질문의 "빠진 부분" 때문인지, 지금 있는 재검색 장치가 작동하는지, 답변의 빈칸(gaps)을 재검색 신호로 쓸 수 있는지.

**1) 질문 해석이 이미 질문을 나눈다.** 여러 부분을 묻는 질문은 과제(task)를 여러 개로 나누거나(예: `EMA_UST_PK_011` → CHMP 질문 / 신청자 설명 / CHMP 최종 평가, 3과제), 한 과제 안에서 부분마다 검색어를 하나씩 만든다(예: `EMA_UST_IMMUNOGENICITY_005` → "NAb 검사법" 검색어와 "NAb 시료 선택 조건" 검색어). H 설정에서 빠진 근거(화면 선택 있음 6개, 없음 12개)를 하나씩 보면, **빠진 부분을 위한 검색어가 없어서 빠진 경우는 없다.** 대부분은 후보 안에 있었는데 순위에서 밀린 경우(리랭커 쪽)다. 후보에도 못 든 1개(005의 49쪽)도 그 부분의 검색어는 있었다.

**2) 지금 있는 재검색 장치(`ra_research.extend`, LLM 없음)는 사실상 작동하지 않는다.** 질문에서 정해진 항목(용량·경로, 비교약, 설계, 표 통계 등 14종)을 규칙으로 찾고, 근거에 없으면 한 번 더 검색한다. 104문항 중 **추가된 근거는 0개**였다. 멈춘 이유는 "빠진 항목을 못 찾음"이 98~103건이었다.

**3) 답변의 빈칸(gaps)은 재검색 신호로 쓸 수 없다.** H 답변(31문항 × 3회 = 93개) 중 빈칸이 없는 답은 4개뿐이다. 그런데 빈칸 대부분은 **질문 전체를 다시 적은 문장**이다(예: C03의 빈칸 = 질문 원문). 정답 근거가 모두 공급된 답에도 똑같이 붙는다. 이걸 신호로 재검색하면 거의 모든 질문에서 재검색과 답변 재생성이 일어난다. 그래서 LLM 비용은 2배가 되는데 얻는 근거는 거의 없다.

| 확인 | 결과 |
| :-- | :-- |
| 답변평가(H)에서 정답 근거가 일부 빠진 문항 | 2개: C03(4쪽 중 3쪽), E04(3쪽 중 2쪽) |
| C03 | 빠진 쪽이 있어도 사실 포함 1.0 (3회 모두). 같은 내용이 다른 쪽에 있음 |
| E04 | 0.75 (2회). 빠진 사실(임상 브리징 조건)은 근거가 공급됐는데 **답변 검토 규칙**(`clinical_bridging_applicability_not_in_final_clause` 등)이 탈락시킴 → 4-2장과 같은 답변 단계 문제 |
| 평가 세트의 여러 제품 비교 질문 | 101문항 중 2개(E03, `EMA_UST_PK_031`). PoC에서 질문 분해가 약했던 유형인데 여기서는 거의 측정되지 않음 |

결론:
- 지금 평가 세트에서는 **질문 분해(재검색)를 만들어도 얻을 근거가 거의 없다.** 질문 나누기는 질문 해석이 이미 하고 있고, 남은 손실은 순위(리랭커)와 답변 단계에 있다.
- 평가 세트에 여러 제품 비교 질문이 2개뿐이어서 비교 질문 세트를 따로 만들어 확인했다(아래 4-5).

## 4-5. 여러 제품 비교 질문으로 질문 분해 재진단

PoC에서 질문 분해가 가장 약했던 유형(비교 질문 정답 근거 38%)을 따로 확인했다. `eval/compare_cases_v1.json`에 비교 질문 8개를 만들었다(2~3개 제품, 정답 단위 19개). 각 제품 부분의 정답 쪽은 `eval/queries_v0.1.csv`에서 같은 주제의 단일 제품 문항(예: Q009 + Q050)의 인정 쪽을 그대로 썼다. 질문 해석 16회, $0.01.

| 조건 | 설정 | 공급 / 19 | 고르기 탈락 | 후보에도 못 듦 | 평균 프롬프트 토큰 |
| :-- | :-- | --: | --: | --: | --: |
| 화면 선택 있음 | 기준 (k=8) | 18 | 1 | 0 | 약 14.7k |
| 화면 선택 있음 | H (리랭커, k=12) | 17 | 2 | 0 | 약 23.4k |
| 화면 선택 없음 | 기준 (k=8) | 18 | 1 | 0 | 약 40.1k |
| 화면 선택 없음 | H (리랭커, k=12) | 18 | 1 | 0 | **약 60.3k** |

- **비교 질문에서도 후보에도 못 드는 근거는 0개다.** 질문 해석은 비교 질문을 과제 1개로 두지만, 검색이 **제품 × 기관 그룹마다 따로** 돌기 때문에 제품별 분해가 구조적으로 이미 일어난다. 같은 검색어(주제 용어 포함)가 모든 제품 그룹에서 쓰이므로 PoC의 문제("제품별 하위 질문에 주제 용어가 빠짐")도 생기지 않는다. → **질문 분해는 비교 질문에서도 만들 필요가 없다.**
- 리랭커는 비교 질문에서 이득이 없었다(화면 선택 있음 18 → 17). CMP06에서 SB17 쪽(기준 순위 3위)을 밀어냈다. 비교 질문의 검색어에는 여러 제품명이 함께 들어가서("ABP654 Wezenla and CT-P43 Steqeyma … dose route"), 리랭커가 다른 제품을 말하는 검색어 기준으로 점수를 매기기 때문으로 보인다. 8문항이라 차이는 작지만 기록해 둔다.
- **화면 선택이 없으면 비교 질문의 프롬프트가 한도에 닿는다.** 그룹이 8~12개(제품 2~3개 × 기관 4개)가 되고, H 설정에서 7/8문항이 약 61k 토큰(한도 65,536)에 이르며 근거 블록이 최대 38개 잘린다(정답 근거는 이번에는 남았다). 그룹 수에 따라 그룹당 k를 줄이는 방식(예: 전체 상한을 정하고 그룹마다 나누기)이 다음 개선 후보다.

## 4-6. 그룹이 많을 때 질문당 전체 상한: 효과보다 손실이 커서 기본값은 끔

화면 선택이 없거나 비교 질문이면 검색 그룹이 많아져 프롬프트가 커진다(4-3, 4-5). 그래서 질문당 전체 검색 결과 수에 상한을 두는 옵션을 넣었다. 그룹당 개수는 `total_hits ÷ 그룹 수`이고, 그룹당 최소 4개, 최대 k(12)다. 프로필 `total_hits`로 켜며 기본값은 끔이다. 109문항(101문항 + 비교 8문항, 정답 175단위)을 저장된 질문 해석으로 다시 돌려 비교했다(LLM 호출 없음).

| 조건 | 설정 | 공급 / 175 | 그룹 6개 이상 질문의 평균 프롬프트 토큰 | 60k 토큰 이상 질문 | 예산 때문에 잘린 근거 블록 |
| :-- | :-- | --: | --: | --: | --: |
| 화면 선택 있음 | H | 167 | 10.2k (1문항) | 0 | 132 |
| 화면 선택 있음 | H + 상한 48 | 167 | 6.7k | 0 | 112 |
| 화면 선택 있음 | H + 상한 36 | 167 | 5.1k | 0 | 102 |
| 화면 선택 없음 | H | **162** | 51.4k (16문항) | 10 | 762 |
| 화면 선택 없음 | H + 상한 48 | 159 | 35.7k | 1 | 181 |
| 화면 선택 없음 | H + 상한 36 | 158 | 30.1k | 1 | 169 |

- 화면 선택이 있으면 그룹 6개 이상인 질문이 1개뿐이라 상한의 효과도 손실도 없다.
- 화면 선택이 없으면 상한 48이 큰 질문의 프롬프트를 약 30% 줄이고 60k 이상 질문을 10개에서 1개로 줄인다. 하지만 **정답 근거를 3개 잃는다**(CMP03·CMP06의 SB17 부분, `EMA_UST_IMMUNOGENICITY_026`). 36이면 4개를 잃는다.
- 이미 있는 **문맥 예산 정리(`ra_retrieval.context`)가 근거를 762개 잘라도 정답 근거는 하나도 잃지 않았다**(예산 제외 0). 고르게 자르는 상한보다 기존 예산 정리가 더 잘 고른다.
- 비용 절감은 큰 질문 하나당 입력 약 15k 토큰, 약 $0.003으로 작다.
- 상한을 켜도 `EMA_UST_PK_011`(그룹 60개)은 그룹당 최소 4개 때문에 61.7k로 남는다. 그룹이 많아지는 근본 원인은 시험 번호만 있는 질문을 질문 해석이 제품에 연결하지 못하는 것이다(6장, 담당 밖).
- 결론: **상한은 기본값으로 켜지 않는다.** 옵션은 남겨 두고, 프롬프트 크기가 문제가 되면 그때 다시 본다.

## 4-7. main 리랭커 기준 재측정 (병합 후, 2026-10-16)

최신 main(병합 `c595296`)에서 109문항(101 + 비교 8, 정답 175단위, 화면 선택 있음)을 다시 진단했다. main의 질문 해석으로 한 번 계획을 만들고(113회, $0.11) 네 설정이 같은 계획을 쓴다. 답변 생성은 하지 않는다.

| 설정 | 공급 / 175 | 리랭커 끔·8개 대비 | 고르기 탈락 | 후보에도 못 듦 | 평균 프롬프트 토큰 |
| :-- | --: | :-- | --: | --: | --: |
| 리랭커 끔, 그룹당 8개 | 153 | — | 21 | 1 | 7.9k |
| **main 리랭커, 8개 (지금 main 기본값)** | **160** | +11 / −4 | 14 | 1 | 8.6k |
| **main 리랭커, 12개 (H 노하우)** | **163** | +12 / −2 | 11 | 1 | 11.2k |
| 리랭커 끔, 12개 | 161 | +8 / −0 | 13 | 1 | 10.7k |

순위 지표 (101문항, 그룹 순위 기준, `eval/post_retrieval_rank_metrics.py`):

| 지표 | 리랭커 끔 | main 리랭커 |
| :-- | --: | --: |
| Hit@5 / @8 / @12 | 0.772 / 0.832 / 0.881 | 0.802 / 0.851 / 0.901 |
| Recall@5 / @8 / @12 | 0.699 / 0.776 / 0.846 | 0.718 / 0.808 / 0.885 |
| MRR | 0.503 | **0.588** |
| NDCG@5 / @8 / @12 | 0.533 / 0.561 / 0.581 | 0.606 / 0.633 / 0.654 |

- main 리랭커는 이 평가 세트에서도 효과가 있다(공급 153 → 160, MRR 0.503 → 0.588). 팀원 기록(검색 골든셋 recall@8 0.715 → 0.804)과 같은 방향이다.
- **H 노하우 ① 그룹당 12개**: main 리랭커에 더하면 160 → 163(+3). 프롬프트는 8.6k → 11.2k(+30%). 리랭커 없이 12개(161)보다도 높다. 이득은 병합 전 H(k=8 → 12에서 +6)보다 작다.
- **H 노하우 ② 검색어별 1위 보장**: main 리랭커는 RRF로 원래 순위와 섞어서 "강한 하이브리드 결과를 혼자 묻지 못한다"고 설계했지만, **하이브리드 1위였던 정답 3개(Q004, Q035, `EMA_UST_PK_002`)가 리랭커 때문에 빠진다**(12개에서도 Q004·Q035는 빠짐). RRF 점수는 하이브리드 1위라도 리랭커가 꼴찌로 보면 1/61 + 1/100 정도라, 하이브리드 2~12위이면서 리랭커가 좋게 본 후보에 밀린다. H에서 쓴 "각 검색어 1위는 먼저 넣기"가 바로 이 경우를 막았다. → 다음 시험 후보(8장).
- **비교 질문**: main 리랭커 8개에서 17/19, 12개에서 18/19. 병합 전 H(17/19)보다 나쁘지 않다. 제품·기관을 질의에 붙이는 main 방식이 4-5장의 문제를 줄인 것으로 보인다.
- 주의: 병합 전 H의 수치(3장)와 직접 비교하지 않는다. 질문 해석(계획기)이 바뀌어서 검색어 자체가 다르다.

## 4-8. main 리랭커 + 검색어별 1위 보장 (H 노하우 ②): 효과 없음, 옵션만 남김

4-7에서 하이브리드 1위였던 정답 3개가 main 리랭커에서 빠졌다. 그래서 H의 1위 보장(각 순위 목록의 1위를 리랭커 순서보다 먼저 넣기)을 main 리랭커에 옵션 `rerank_keep_first`(기본 꺼짐, 함수 `keep_first_hits`)로 넣고, 같은 계획으로 비교했다(LLM 호출 없음).

| 설정 | 공급 / 175 | main 리랭커 대비 | 평균 프롬프트 |
| :-- | --: | :-- | --: |
| main 리랭커, 8개 | 160 | — | 8.6k |
| main 리랭커 + 1위 보장, 8개 | 158 | +3 / −5 | 8.3k |
| main 리랭커, 12개 | **163** | — | 11.2k |
| main 리랭커 + 1위 보장, 12개 | 163 | +2 / −2 | 11.1k |

| 지표 (101문항) | main 리랭커 | + 1위 보장 |
| :-- | --: | --: |
| Hit@5 / @8 / @12 | 0.802 / 0.851 / 0.901 | 0.792 / 0.871 / 0.911 |
| Recall@5 / @8 / @12 | 0.718 / 0.808 / 0.885 | 0.718 / 0.814 / 0.891 |
| MRR | **0.588** | 0.507 |
| NDCG@8 / @12 | **0.633 / 0.654** | 0.573 / 0.593 |

- 1위 보장은 노린 3개(Q004, Q035, `EMA_UST_PK_002`)는 살리지만, 1위 자리가 리랭커가 고른 다른 정답을 밀어내 5개(8개 기준)를 잃는다. 12개에서는 +2/−2로 같다.
- 순위 지표는 Hit·Recall이 조금 오르고 MRR·NDCG가 크게 떨어진다. 정답을 위쪽에 두는 능력은 main의 RRF 방식이 낫다.
- 결론: **main 리랭커에는 1위 보장을 넣지 않는다.** 병합 전 H에서 효과가 있었던 건 H가 RRF 없이 리랭커 점수만으로 정렬했기 때문으로 보인다. main은 RRF가 이미 그 역할을 대부분 한다.
- H 노하우 중 남는 후보는 **그룹당 12개**(160 → 163, 프롬프트 +30%)다. 답변 점수로 확인한 뒤 정한다.
